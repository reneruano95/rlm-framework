# Server: a slot that has held one document injects its content into a later, unrelated request on the same slot

## Summary

On `llama-server`, a slot that has previously held one prompt can inject that
prompt's content — including 128-bit identifiers that appear nowhere else — into
the response to a later, unrelated prompt routed to the same slot.

Paired measurement, one process, byte-identical prompts issued to both arms at
the same moment; the arms differ in exactly one thing, whether the slot has
previously held a *different* document:

| build | shared pinned slot | one fresh slot per document | Fisher exact (2-sided) |
|---|---|---|---|
| `b10488-9d77fa172` (current) | **37 / 54** | **0 / 54** | p = 8.3e-16 |
| `b10375-ba360efe1` | 35 / 54 | 0 / 54 | p = 1.3e-14 |

Counting only full UUIDs — a 128-bit value minted for one document and appearing
in an answer about another, which cannot occur by chance — the same runs give
**4/54 and 2/54 on the shared slot, 0/54 on fresh slots.**

The effect:

* survives a full re-prefill in which the server itself reports
  `timings.cache_n == 0`;
* survives `POST /slots/{id}?action=erase`, which returns 200 with a truthful
  non-zero `n_erased`;
* grows with the number of distinct documents the slot has previously held;
* disappears completely when each document is given a slot that has held nothing
  else — same process, same weights, same prompt bytes, same sampler;
* occurs on both a hybrid attention/SSM model and a pure-attention model, so it
  does not appear to be about recurrent-state handling.

## Environment

```
build       b10488-9d77fa172   (also reproduced on b10375-ba360efe1)
backend     HIP / ROCm 7.14, Windows 11, gfx1151 (Radeon 8060S, Strix Halo)
```

Models — reproduced on both:

* `Qwen3.6-35B-A3B` UD-Q4_K_M — GGUF arch `qwen35moe`, hybrid attention + SSM
  (`ssm.state_size = 128`, `full_attention_interval = 4`).
* `gemma-4-12B-it` Q8_0 — GGUF arch `gemma4`, **no `ssm.*` keys**; the loader
  allocates only non-SWA + SWA KV caches, no recurrent state. It leaked at least
  as much as the hybrid model, which is why I do not think this is the known
  hybrid/recurrent prompt-cache issue.

## Launch line

```
llama-server --host 127.0.0.1 --port 8081 -m <model.gguf> \
  -c 327680 -np 8 -ctk q8_0 -ctv q8_0 -fa on -ub 512 -b 2048 \
  -lm none --no-kv-unified --cont-batching --slot-save-path <dir>
```

`--slot-save-path` is only needed for the `action=erase` part of the test; the
leak reproduces without it.

## Reproducer

`r13_repro.py` (attached) is self-contained — standard library plus `httpx`,
sharing no code with the harness that originally found this. The corpus is six
documents of 1,021 / 2,045 / 4,094 / 8,190 / 16,382 / 32,766 tokens, each
containing one coined organisation and one UUID that appear in no other
document, generated by the attached `make_fixtures.py`.

```
python r13_repro.py --port 8081 --replay-fixtures ./fixtures --replay-trials 3 \
  --temperature 0.3 --n-predict 512 --slot 0 --paired-virgin --out results.jsonl
```

For each document, in ascending order of length, the same prompt is sent twice:
once to slot 0 (which has already held every earlier document) and once to a
slot that has never held anything. A hit is an answer containing an identifier
or coined organisation that is absent from the document sent **and** absent from
the question asked, and present in a different document.

## Expected

Each response references only the document it was sent. A slot's previous
occupant is invisible.

## Actual

From the second document onward, answers on the shared slot describe or quote
earlier documents. The same prompt sent to a fresh slot in the same process at
the same moment does not.

Document 3 (4,094 tokens), asked about an organisation that is in **no**
document, `b10488`:

```
shared slot 0 (has previously held documents 1-2):
  The provided text contains custody notes for the "Prylfennwick Trust"
  (key: 1251d802-86aa-4e75-96be-aefc175c1e8e) and the "Orstlornholm Trust" ...

fresh slot (has only ever held document 3):
  The provided text contains no custody note for that organisation.
```

`1251d802-86aa-4e75-96be-aefc175c1e8e` is document **1**'s UUID. It is not in
document 3, and it is not in the question. The same UUID leaked into answers
about documents 2 and 4 in the same run.

Leak rate by position in the sequence, shared slot, three trials agreeing:

| document | 1st | 2nd | 3rd | 4th | 5th | 6th |
|---|---|---|---|---|---|---|
| leaked | 0 | 3 | 6 | 8 | 8 | 9 |

Two documents on one slot is enough.

## Two observations that may narrow it down

**1. It is not the prompt cache.** The first request against each new document
reports `timings.cache_n == 0` — nothing reused, whole prompt prefilled — and
several such requests still returned earlier documents' content.

**2. It is not what `action=erase` clears.** Issuing
`POST /slots/0?action=erase` before each document returns 200 with a truthful
`n_erased` (1231, 2221, 4271, 8364, 16562 — matching the resident prompt
lengths), and the leak rate is unchanged: 33/54 with erase, 34/54 without.

Together these suggest per-slot state that is neither counted by `cache_n` nor
released by `erase`.

## Possibly related

#24746 (closed, fixed by #24755) found that requests specifying `id_slot`
bypassed `get_available_slot()` and so skipped prompt-cache preparation
entirely; the fix introduced `get_slot_for_task()` to unify the two paths. That
issue was purely about cache-reuse efficiency, not content, and this leak still
reproduces on `b10488`, which includes that fix. I mention it only because it
shows the explicit-`id_slot` path has diverged from the implicit one before, and
this reproducer pins `id_slot` on every request.

## What did not reproduce

Two documents of 522–8,551 tokens built from high-entropy random filler with one
freshly minted UUID each, across `cache_prompt` true/false, same slot and
different slot, A→B→A ordering, changed `seed`, `n_keep: 0`, and
`save`/`restore` — 110 trials, zero leaks. An independently written generator
producing cleaner synthetic prose also failed to reproduce it (0/36).

The effect needs the long, repetitive, low-entropy corpus, and it shows up far
more readily under a question that asks what the document contains than under
one with a single expected answer. I have not read the server source, so I have
no hypothesis about which code path is responsible.

## Minor, possibly separate: `action=erase` reports 501 for a misleading reason

Without `--slot-save-path`, `POST /slots/{id}?action=erase` returns
`501 This server does not support slots action. Start it with --slot-save-path`.
`erase` neither reads nor writes a file, so gating it on the save path is
surprising, and the message sends you looking for a build without the feature. I
originally concluded the endpoint was unimplemented because of it. Happy to open
that separately if it is worth its own issue.
