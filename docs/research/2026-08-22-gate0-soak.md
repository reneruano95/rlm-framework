# S6 Gate 0 — can a local 27B sustain a long-horizon loop on this box?

**Date:** 2026-08-22 · **Status:** measured. **T-1, T-2 and T-4 PASS.** T-3 withdrawn as mis-designed by me; see §5.
**Gate:** `docs/superpowers/specs/2026-08-22-long-horizon-agent-design.md` §5.1.
**Server:** root only, `b1-5ecbe1a` (the unmerged DFlash2 PR that `config.yaml:106` pins), Qwen3.8-27B-Q4_K_M + DFlash2 drafter, `-c 32768 -np 1 -ctk q8_0 -ctv q8_0 -fa on -lv 4`, launched via the project's own `launch_argv` so the flags are exactly what the config specifies.
**Frames:** 8 real 64×64 observations from `ls20-9607627b`, pulled through the ARC-AGI-3 SDK and cached. The SDK issues an anonymous API key on its own; no key was configured.
**Scope:** nothing in this ran through `rlm`. The soak drives the root server directly over HTTP, so a failure here is the server's and not the scaffold's — which is the point of a gate that decides whether to build the scaffold.

---

## 0. The short answer

**The two objections that would have killed the programme are both answered, and the one that survives is neither of them.**

The context horizon is not a wall: the right serialisation puts a 64×64 frame in **447 tokens**, against **12,438** for the format the official ARC harness sends. Twenty-eight times. And the append-only prefix cache does not degrade — it reaches **98.6%** and stays there while the context grows ninefold.

And 82% of the per-turn cost was llama.cpp writing context checkpoints that **nothing ever restores** — `-ctxcp 0` takes the turn from **13.9 s to 2.5 s** with the prefix cache untouched.

What binds is then arithmetic nobody was disputing: a 32K window holds **70 turns** at 467 tokens each. The loop does not fail. It finishes — now in **under three minutes** — having taken seventy actions.

## 1. T-1 — tokens per observation · **PASS**

Threshold: at least one serialisation ≤ 1,000 tokens/frame. That number is not round for its own sake — it is the measured fact-cliff bracket [967 pass, 1,022 fail], 30/30 vs 0/21, reproduced across two model families.

Median over 8 frames, tokenised by the root's **own** `/tokenize`:

| serialisation | tokens | range | chars | tok/char |
|---|---:|---|---:|---:|
| `int_rows` — one Python int list per row, what the official harness sends | **12,438** | 12,431–12,445 | 12,438 | **1.00** |
| `glyph_rows` — one character per cell | 788 | 778–793 | 4,159 | 0.19 |
| `segmentation` — connected components, in Duck Harness's shape | **447** | 426–448 | 762 | 0.59 |

**Measuring beat estimating, in both directions.** The prior "rendered ARC grids are close to 1 char per token" is exactly right for `int_rows` — 1.00, to two decimals. The tokenizer compresses *nothing* in a stream of digits, commas and brackets. But it is badly wrong for the serialisations that matter: structured text runs 0.19–0.59 tok/char. A chars/4 proxy would have estimated `int_rows` at ~3,100 tokens and been wrong by a factor of four, **in the optimistic direction** — it would have said the official format nearly fits when it does not fit at all.

The 28× gap between the top and bottom rows is the whole finding. It confirms by measurement what Duck Harness (1st place, ARC-AGI-3 Milestone 1, Qwen3.6-27B served locally) does by construction: **do not show the model the grid.** Expose objects and let the REPL do the seeing. That is I2 — "context by reference, the full context never enters a message array" — arrived at independently by someone who won money with it.

## 2. T-4 — prefix cache under append-growth · **PASS**

Threshold: `tokens_cached / tokens_in` ≥ 0.90.

| turn | tokens_in | cached | wall |
|---:|---:|---:|---:|
| 1 | 495 | 6.1% | 14.9 s |
| 8 | 3,753 | 88.1% | 14.8 s |
| 16 | 7,486 | 94.0% | 14.4 s |
| 32 | 14,954 | 97.0% | 15.2 s |
| 48 | 22,422 | 98.0% | 15.5 s |
| 70 | 32,706 | **98.6%** | 14.4 s |

The threshold is cleared from turn 16 and never dips after. An append-only conversation is the best case for a prefix cache and llama.cpp delivers it — the "context that grows over hundreds of turns" objection is answered.

**RSS grew 3.3%** across the measured span (6,090 → 6,293 MB, turns 25→50). No leak at this timescale.

## 3. The claim I got wrong, and the correction

Reading the first five turns, I reported that `prompt_ms` was "growing with context — if that slope holds, turn 60 is unviable."

**It was cache warm-up, not a slope.** Over turns 8→70 the context grew **9×** (3,753 → 32,706 tokens) and latency did not move:

- median wall, turns 8–20: **14.56 s**
- median wall, turns 58–70: **14.32 s**

The per-turn cost is **fixed and context-independent**. Five turns was not enough data to tell a warm-up transient from a trend, and I called it before it was.

## 4. What actually ended the run — and it was not a crash

Turn 71 returned **HTTP 400**, not a failure:

```
slot: task 408 | new prompt, n_ctx_slot = 32768, task.n_tokens = 33176
srv send_error: request (33176 tokens) exceeds the available context size (32768 tokens)
slot release: task 408 | stop processing: n_tokens = 32708, truncated = 0
```

`/health` answered `ok` afterwards. The server refused cleanly and stayed up. **My harness logged this as "server died", which was wrong** — a rejection is not a death, and the difference is the difference between "this box cannot do it" and "this window cannot hold it."

At **467 tokens per turn** (447 frame + reply + template), 32,768 tokens is **70 turns**. That is not a defect. It is division.

---

## 5. T-3 — withdrawn, mis-designed

The threshold as written — "one process completes ≥ 2,000 sequential requests" — cannot be met by the experiment I built. 2,000 turns × 467 tokens is 936K tokens; no single conversation holds that in any window this box can afford.

**Process endurance and prefix-cache durability are two experiments, and I fused them into one.** Endurance needs many short conversations against one server process; cache durability needs one long conversation. Upstream llama.cpp issue #23181 (1,500–2,000 sequential requests, crash in 30 min–3 h) is about *requests*, not turns, so the correct test is a loop of short conversations. It has not been run and nothing here says anything about it.

## 6. T-2 — the checkpoint tax · **PASS**, and larger than forecast

Threshold: some `-ctxcp` cuts median turn wall ≥ 30% **without** forcing a full re-prefill. Same 70-turn soak against each setting, server relaunched between.

| `-ctxcp` | median wall | vs default | checkpoints created / erased / **restored** | cached at turn 70 |
|---:|---:|---:|---|---:|
| 32 (default) | 13.88 s | — | 209 / 202 / **0** | 0.9857 |
| 1 | 13.82 s | −0.4% | 209 / 0 / **0** | 0.9857 |
| **0** | **2.48 s** | **−82.2%** | 0 / 0 / 0 | **0.9857** |

**The spec's hypothesis is confirmed literally: 209 checkpoints created, zero restored.** On an append-only loop nothing rewinds, so a checkpoint is written and thrown away. That is not a subtle inefficiency — it is **82% of the turn**.

**And the claim that `-ctxcp 0` forces a full prompt reprocess is refuted.** The cached fraction is identical to four decimals across all three settings — 0.9857 — so the latency is bought with nothing. That was the trap this comparison existed to catch, and it is not there. Recording cache alongside latency is what makes the result usable; a wall-clock win with a collapsed cache would have been a loss wearing a win's numbers.

**The spec under-forecast it.** It estimated ~8.3 s of a ~15 s turn (−55%). Measured: **11.4 s of 13.9** (−82%).

`-ctxcp 1` is the control that makes the mechanism unambiguous: same 209 creations, none erased, same latency. The cost is in *writing* the checkpoints, not in managing them.

## 7. What this changes

**The programme-kill criterion did not fire**, and neither of its two halves came close.

The binding constraint has moved from *"can the model read a frame"* and *"does the history degrade"* — both settled — to a straightforward budget:

| | at 32K (today) | at 262K native |
|---|---:|---:|
| tokens per turn | 467 | 467 |
| turns before the window refuses | **70** | ~505 |
| wall clock, at the default 13.9 s | 16 min | 1.9 h |
| wall clock, at `-ctxcp 0`'s 2.5 s | **2.9 min** | **21 min** |
| KV cost | — | 8.5 GiB of 128 |

Raising `ctx` is a config change, not a capability. The spec already notes the official ARC harness assumes `MAX_CONTEXT_LENGTH: 175,000` with front-trimming, and that root KV is 34.0 KiB/token.

So the question that remains is a **properly designed T-3**: does one server process survive 2,000 requests across many short conversations? That is the one upstream issue #23181 is about, and nothing here touches it.

**`-ctxcp 0` should be considered for `config.yaml`'s root block, and not on this evidence alone.** The soak is append-only by construction, which is precisely the workload a checkpoint cannot help. A real episode may rewind — and if it does, the 82% is a discount on a service the scaffold actually uses. Measure a real episode both ways before pinning it.

**What is not yet touched:** whether a 27B can actually infer mechanics from a segmentation summary and choose a useful action. Gate 0 measures the plumbing. That question is §5.3's afternoon probe — twenty frames, hand-scored — and it is the one that decides whether any of this is worth building.

## Reproducing

The harness lives in this session's scratchpad, not in the repo — a one-off measurement does not need to live in the product tree; its conclusion does. It needs `arc-agi` + `arc-agi-3` in a venv of their own, which have no business in `pyproject.toml`.

```
gate0_soak.py --phase capture --game ls20-9607627b --frames 8
gate0_soak.py --phase tokens                 # T-1
gate0_soak.py --phase soak --turns 80        # T-4, and the window ceiling
t2_ctxcp.py                                  # T-2, relaunches the server three times
                                             #      records cache WITH latency -- a win
                                             #      bought by losing the prefix is a loss
```

Two things the harness must keep doing, both learned by getting them wrong first:

- **Disable thinking explicitly** (`chat_template_kwargs: {enable_thinking: false}`). `config.yaml` sets it, but the *scaffold* applies it — driving the server directly bypasses that, and the model then spends its whole token budget in `reasoning_content` and returns an empty reply. It would also measure the wrong thing: thinking is known to collapse the root's prefix reuse, so T-4 would fail for a reason unrelated to the loop.
- **Read cached tokens from `timings.cache_n`** (or `usage.prompt_tokens_details.cached_tokens`). The plausible-looking names — `prompt_n_cached`, `usage.cached_tokens` — do not exist and return null on every turn, which reads as "no cache" rather than as "wrong field."

# 8. The 20-frame probe — §5.3's precondition · **PASS**, carried by one item

Gate 0 measured the plumbing. This asks the question that decides whether the
plumbing is worth using: **given a segmentation summary rather than a raw grid,
can Qwen3.8-27B read the state and attribute what an action did?**

Pre-registered before any prompt ran; two dated addenda record what had to
change and why.

## The result

| item | model | best degenerate strategy | verdict |
|---|---:|---:|---|
| **Q3b — name every changed object** | **9/14** | 2/14 (best constant set) | **PASS**, by 7 |
| Q5 — the changed object's bbox after | 14/14 | 11/14 (`copy BEFORE, x0+1`) | corroborating, thin |

Verdict rests on **Q3b**. Q5 points the same way but its real evidence is
**3 items**: eleven of the fourteen come from `ls20`, whose target object is a
progress bar advancing one column per action, and the arithmetic bluff scores
those eleven perfectly. On the three items from another game the model is 3/3
and the bluff is 0/3.

## Getting here took three item sets and three bluffs

Every version passed on its face. Every version was then tested against the
degenerate strategy its own ground truth permitted, and two of three died:

| bluff | found by | outcome |
|---|---|---|
| "always name the largest object" | pre-registered | scored 0 — the control worked |
| "always name the same object" | **missed** | `obj10` scored **20/20** vs the model's 19 — **Q3 void** |
| "copy BEFORE's bbox, add 1" | **missed** | scored **20/20**, identical to the model — **Q5 void on set 1** |

And two items I had counted as passing were never measuring anything: `Q1`
(object count) had two distinct truths across twenty items, so "always say 21"
scored 19/20; `Q2` (largest object) had **one** truth — `(4, 2509)` in all
twenty — so a constant scored 20/20.

**The defect was never the questions. It was the items.** `ls20`'s first twenty
steps with actions cycled 1,2,3,4 are a near-static world: the same 21 objects,
the same largest object, four toggling, a bar advancing. No question asked of
that set can discriminate, because the set does not vary.

The fix was to build variety into the items — random actions across every
anonymously reachable game, keeping a transition only when fewer than two
existing items already share its changed-set. Yield: 14 items, 2 games, **12
distinct changed-sets** where there had been 6, which is what drops the best
constant from 9/20 to 2/14.

**The reusable lesson: a control has to be derived from the ground truth's
distribution, not imagined.** I guarded the bluff I thought of and missed the
two the data actually permitted. Three checks, three bluffs — and the only
reason any of them surfaced is that the check is now mandatory for every item
rather than a per-item afterthought.

## What this licenses, and what it does not

**Licensed:** the segmentation representation is legible to this model, and
`§5.3`'s precondition is met. Gate 2's `env_step` spike is worth building.

**Not licensed:** anything about play. One-step attribution on a labelled
transition, with BEFORE and AFTER both supplied, is the easiest question in this
space. The model was never asked to choose an action, plan, or infer a rule it
was not shown.

**And the evidence is thinner than the spec asked for:** 14 items, not 20; two
games, not several. Three of the six reachable games return a frame shape the
harness does not handle, and 25 environments are listed but most need an API key
the anonymous one does not cover. A wider set would make Q5 mean something on
its own instead of resting on three items.

**Not measured, and it is the next question:** whether the model can propose a
*useful* action. The probe recorded free-form action proposals (`Q4`) and
deliberately excluded them from PASS/FAIL, because nothing about them is
auto-scorable and hand-scoring my own probe is how the first three bluffs got
through.
