# S6-lite v0 — implementation plan

**Date:** 2026-08-27 · **Status:** APPROVED 2026-08-27; step 1 in progress.
**Spec:** `docs/superpowers/specs/2026-08-27-s6-lite-v0-artifact-gate.md` — approved by the owner 2026-08-27, including both §10 answers: the **local root is the proposer** (an assumption, not an arm), and the **positive control is in scope**.
**Evidence this consumes:** `docs/research/2026-08-27-prime-agent-spike.md` and its committed artefacts under `docs/research/2026-08-26-prime-agent-spike/`.
**Shape of the work:** six steps. Steps 1–3 build the instrument, step 4 **validates it against a known-good and a known-bad input before it is trusted**, step 5 runs the real loop, step 6 writes it up. Each step states how we know it worked; a step whose check fails stops the plan rather than being worked around.

---

## 0. Order, and why this order

The gate is an instrument. An instrument that has only ever said "no" is not known to work — that is §10's answer and it sets the sequence: **the positive and negative controls run before the proposer exists.** The spike handed us both fixtures already committed:

- **known-good** — the cross-check instruction that made Phase C write two independent counters and reconcile all seven files, where Phase A, unasked, shipped `1` against 1,323 records. Expected verdict: **ACCEPT**.
- **known-bad** — the actual `harness_state.json` the local root wrote, committed at `docs/research/2026-08-26-prime-agent-spike/results/phase-b/harness/`. Its held-out arm measured 2/3 and 2.2× wall. Expected verdict: **REJECT**.

If the gate cannot separate those two, nothing downstream means anything.

**Budget.** One gate decision = 9 held-out tasks × 3 seeds × 2 arms = **54 episodes**, ~50–75 min at the spike's measured medians. The plan spends **5 decisions** (positive control, negative control, up to 3 proposer rounds) ≈ 5 h of runs, inside D-S6's cap of 5.

## Step 1 — vendor, pin, and prove the three seams

Nothing here is rlm-halo logic; it is establishing that the seams the spec depends on exist and fail loudly when they do not.

- [ ] **1.1** Pin prime-agent at **0.8.1** in a recorded location (`PRIME_AGENT_VERSION=0.8.1`), reusing the spike's isolated `spike`-style WSL user and agent dir. Record the installer sha256 as the spike did.
- [ ] **1.2** Write `.prime/agent/extensions/rlmh-gate.ts` — one file, plain TS via jiti, no build step. At load it registers the three handlers and **asserts each is registered**, throwing at startup if the API shape changed:
  - `session_before_refine` → returns `{skip: true}` unless the round carries the gate's own marker.
  - `before_agent_start` → rebuilds the `# Continual Harness State` block from the accepted set on disk.
  - `refine_complete` → appends to the gate's ledger (notification only; it cannot veto, and the code must not pretend otherwise).
- [ ] **1.3** Settings: `autoRefine.enabled: false`, `rlmMaxDepth: 1`, `idleEvictionMinutes: "off"`, `retry.provider.timeoutMs: 3600000` — the spike's verified-good set.

**How we know it worked.** Three adversarial checks, each of which must fail the way the spec claims:
1. A session that calls `await refine.run()` from the kernel produces **no** change to `harness_state.json` (the `{skip:true}` veto fires). This is the mechanism the spike had only as a prompt instruction.
2. An entry written **directly** into `harness_state.json` by kernel code (`rlm.harness.create_memory(...)`) does **not** appear in the model's system prompt on the next turn (`before_agent_start` filtered it). Verify by asking the model to repeat its harness block.
3. Removing one handler makes launch fail with a named error, not a silent degrade.

## Step 2 — freeze the split, build the runner

- [ ] **2.1** Write `bench/splits/s6lite-v0.json`: the 10 train / 9 held-out assignment from spec §6, each task with its `question_sha256` so the within-shape property is checkable, plus the exclusions (agg-01/02/03, all synthesis) **with their reasons in the file**. Compute and record the split file's own sha256.
- [ ] **2.2** Promote the spike's measurement tooling from `docs/research/2026-08-26-prime-agent-spike/tools/` into a proper module (`src/rlm/gate/` or a sibling — placement is the implementer's call, but it must be import-lint clean per `tests/test_import_rules.py`, which means it may not import the dispatcher). `score.py` and `usage.py` already parse the v0.8.1 JSONL shape correctly against real files [V].
- [ ] **2.3** The runner: given a task list, a seed list, and a `harness_state.json` (or none), run the episodes **in `(task, seed)` blocks with ON and OFF adjacent in time**, capture `metrics.pre/post`, `answer.txt`, wall and exit, and snapshot the harness sha before and after each episode.

**How we know it worked.** Re-run **three held-out tasks × 3 seeds with an empty harness** and reproduce the spike's Phase A numbers within noise for those tasks (codeqa-05 was 3/3 at 47.1 s median, 5,294 tokens). A runner that cannot reproduce a measurement we already have is not yet a runner. Also assert: every episode's recorded harness sha equals the one the arm intended — a mismatch voids the block.

## Step 3 — the screens, tested against real rejects

- [ ] **3.1** Implement S-kind, S-I1, S-answer, S-corpus per spec §3.4. S-I1's keyword set is **generated from `src/rlm/config.py`'s schema**, not hand-typed, so a new budget key cannot silently escape it. S-corpus reuses `rlm.serve.leakcheck` with a `ChunkIndex` over the **held-out** corpora.
- [ ] **3.2** Each screen carries its blind spot in its docstring, in the style `leakcheck` already uses for its two documented limits — S-corpus must say **integers are not identifier-shaped**, which is why `514` and `589` pass it.

**How we know it worked.** A fixture suite built from material already in the repo:
- The four committed `codeqa-harness_state.after-*.json` entries **pass** S-answer (they name train answers, which are legal) — proving the screen does not over-reject.
- A synthetic entry containing `needle-05`'s UUID **fails** S-corpus.
- A synthetic entry containing codeqa-06's answer **fails** S-answer.
- An entry saying "raise `max_wall_clock_s` to 3000" **fails** S-I1; one saying "allow yourself more time before giving up" **passes** — the documented blind spot, pinned by a test so it can never be mistaken for coverage.

## Step 4 — validate the gate with a known-good and a known-bad

This is the step that makes the rest meaningful. **No proposer exists yet.**

- [ ] **4.1** Implement the accept rule: Q (no held-out task lost, ≥2/3 seeds per §8) and K (median per-task ON/OFF token ratio ≤ 0.90 with a 10,000-resample paired bootstrap 95% CI upper bound < 1.00). Report the grid, both statistics, the wall and energy annotations, and the in-window entry count per arm (spec R4).
- [ ] **4.2** Implement the audit record: one row per decision — candidate ids, content sha256s, screen verdicts, the ON/OFF grid, Q and K, accept/reject, the resulting harness sha256, and the split's decision ordinal (D-S6's cap of 5).
- [ ] **4.3** **Positive control.** Hand-author one `prompt` artifact carrying Phase C's cross-check instruction — the procedure, no answers, no corpus strings. Record its text and sha256 **before** the run. Run one full gate decision.
- [ ] **4.4** **Negative control.** Take the committed `archived-global-before-C-*.json` (the promoted code-QA state, four answer-log memories) verbatim as the candidate set. Run one full gate decision. Note it will fail **S-kind** immediately (all four are `memory`), which is itself informative — so also run it with S-kind bypassed, to exercise the empirical gate rather than only the structural screen, and record both.

**How we know it worked.** The pre-registered expectations, fixed here before either run:
- **4.3 must ACCEPT.** If it rejects, either the artifact does not help (a real and publishable finding about E3, which the spike's Phase C evidence makes unlikely) or the instrument is mis-built. Diagnose before proceeding — **do not tune the threshold to make it pass.**
- **4.4 must REJECT** on the empirical gate with S-kind bypassed, and its measured direction should resemble the spike's (held-out worse or more expensive).
- If both land as expected, the gate is demonstrated in both directions and step 5 may run. If either does not, the plan stops here and the failure is written up — a gate that cannot separate these two fixtures is the finding.

---

## Step 5 — the proposer, and up to three rounds

- [ ] **5.1** The proposer: an offline pass by the **local root** over the train split's session JSONLs, emitting candidate `prompt`/`skill` entries under a schema that forbids naming any count, path, identifier or entity from a corpus. It reads trajectories — tool calls, results, outcomes — never a live conversation.
- [ ] **5.2** Run round 1: proposer → screens → gate. Record everything, including **every rejected candidate**, so the proposer's own hit rate is measured rather than inferred.
- [ ] **5.3** Rounds 2 and 3 as needed, up to D-S6's cap of 5 total decisions on this split (4.3 and 4.4 have already spent two).

**How we know it worked.** The instrument is already validated by step 4, so step 5 cannot fail in a way that invalidates it — it can only produce a result. Two of them are acceptable:
- Something passes → the loop closed on local weights, and the accepted artifact is a sha-pinned, held-out-gated, reversible object with a full audit trail. That is the deliverable.
- Nothing passes in three rounds → spec R1's pre-registered response fires: **v0 stops and the proposer is what gets revisited, not the gate.** The finding is stated plainly: *a competent local root's self-proposed artifacts do not survive a held-out cost gate*, with the positive control proving the gate can say yes.

## What would make me stop and re-plan

Pre-registered so it is not decided under pressure:

| trigger | response |
|---|---|
| Step 1's veto check fails — the model can still self-refine | Stop. Without structural I1 enforcement this is prime-agent with extra steps, and the whole option-C argument rests on it |
| Step 2 cannot reproduce the spike's Phase A numbers | Stop. The runner is measuring something else |
| Step 4.3 rejects the positive control | Stop and diagnose. Do **not** move the threshold |
| A held-out episode runs with a harness sha other than its arm's | Void the block and re-run it. A silent mismatch is the one bug that would let an accepted artifact be accepted for the wrong reason |
| The split absorbs a 6th decision | Retire it (D-S6) and record why |

## Not in scope

Delegation, benchmark v2, `config_snapshot` artifact pinning (D-S5), `memory` and `subagent` artifact kinds, synthesis and the regex-solvable aggregation tasks, and any online variant where the artifact store mutates during a scored run (C-1).
