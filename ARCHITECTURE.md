# ARCHITECTURE.md — RLM Runtime (working name: `rlm-halo`)

**Spec version:** `rlm-runtime-spec-v0.3.4` (changelog: §14)
**Status:** Pre-implementation constitution. No code exists. §7 carries community-measured priors (off-box, mid-2026 gfx1151 data — §13); every number is still replaced by S0 on-box measurements.
**Amendment rule:** Invariants (§3) and gates (§9) change only with a version bump and a dated changelog entry. §7 numbers and §4 sizing update in place as measurements land, no bump required.
**Hardware target:** AMD Ryzen AI MAX+ 395 "Strix Halo", 128 GB unified LPDDR5X, 256 GB/s theoretical (~212–215 GB/s measured) bandwidth, Radeon 8060S iGPU (RDNA 3.5, gfx1151).
**Prime directive:** The LLM proposes; the scaffold disposes.

---

## 1. Purpose & Scope

A local Recursive Language Model (RLM) runtime: a deterministic scaffold that lets a *root* LLM inspect and decompose arbitrarily large contexts through a persistent Python REPL, delegating chunk-level work to cheap parallel *leaf* LLM calls. Context is passed **by reference** (a Python variable), never by value (never in a message array).

**This project is:**
- A serving topology (two resident `llama-server` processes with distinct roles).
- A deterministic scaffold (sandbox, dispatcher, budgets, truncation, tracing).
- A frozen benchmark and a measurement discipline.

**This project is not:**
- An agent framework, a chat product, or a general orchestrator.
- A training project. Learning loops are S6, explicitly unscheduled (§9).
- A simulator host. World models never enter the runtime loop (Invariant I3).

Primary reference: Zhang, Kraska, Khattab — *Recursive Language Models*, arXiv:2512.24601. Full reference list: §13.

## 2. Thesis

This is Thesis B (author's framework — external reference, §12) applied to context management. Deterministic logic renders all control decisions: truncation caps, recursion budgets, routing, termination, and logging are scaffold configuration. The LLM's only powers are (a) writing code that runs in a sandboxed REPL and (b) requesting sub-calls through a dispatcher it does not control. Ground truth lives in the real REPL and in shared artifacts (traces), never in model output taken at face value.

Corollary for performance — **REWRITTEN v0.3.1, forced by R14. The original claim was "the architecture optimizes for many cheap PARALLEL leaf calls over one smart slow context window." Parallelism is now measured to cost quality catastrophically, so that sentence is false on this stack.** Measured: serial dispatch 31/32 correct, 2 calls in flight 9–10/32, 4 in flight 5/32, 8 in flight 2–20/128 — and fan-out at 2 in flight buys 13% of wall-clock while costing 68% of the answers. Serial wins on *correct answers per second* by 2.7×–110× at every level. **`scaffold.dispatch_concurrency` therefore ships at 1** (§10 R14).
The corollary that survives is narrower and is the one the project must now defend: **the architecture trades wall-clock for the only regime in which answers are trustworthy at all.** Every token beyond ~1,000 from the question is effectively invisible to this leaf (§7 #2), so a single long-context pass does not merely run slower per token — it cannot see most of its own input. Chunking to within the horizon is what buys correctness; serial dispatch is what preserves it. **This means the RLM arm is expected to be SLOWER than the B1 single-pass baseline on the §8 primary metric** (~1,180 s serial for a 200K-token corpus against a ~624 s single-pass reference), and the thesis it must now win on is quality-at-a-known-cost, not speed. If S4 shows B1 matching RLM's *accuracy*, the project has no remaining claim — that is the honest bar, and it is a harder one than §2 originally set.

## 3. Invariants

Violating any of these is a bug, regardless of benchmark results.

- **I1 — The LLM proposes; the scaffold disposes.** Truncation caps, budgets, routing, and termination live in `config.yaml` and scaffold code. No model output, prompt content, or REPL side effect may alter them at runtime.
- **I2 — Context by reference.** The full context never enters any model's message array. Models see only scaffold-truncated views (`print` output capped by C3).
- **I3 — Real environment only in the runtime loop.** No simulator or world model may sit between the root and the REPL, or between the scaffold and the final answer. World models are lifecycle tools (training data generation, S6) — never runtime components.
- **I4 — Every episode is a trajectory.** All runs are logged as `(state, action, observation)` steps with a terminal outcome (§6; the state-reconstruction rule is stated there). A run that is not logged did not happen.
- **I5 — Quality gates precede performance work.** No optimization is merged without the frozen benchmark (§8) showing task success unchanged or better. Tokens/sec alone never justifies a change.
- **I6 — Models are config.** Model identity, quant, context sizes, ports, and budgets live in one `config.yaml`. Swapping a model must require zero code changes (S5 gate).
- **I7 — Evaluate only against the real REPL.** Future training (S6) may consume synthetic or simulated environments; evaluation gates may not.

## 4. Serving Topology (Capa 0)

*("Capa" = layer: Capa 0 serving → 1 scaffold → 2 performance → 3 measurement. Each layer may depend only on the ones below it.)*

Two `llama-server` processes, both resident simultaneously. Not LM Studio — we need `--parallel`, continuous batching, explicit KV cache types, and prompt-cache control.

| | **ROOT** | **LEAF** |
|---|---|---|
| Model | Qwen3.6-27B — dense FFN, **hybrid attention** (16/64 layers carry KV, rest Gated DeltaNet; multimodal, mmproj unused) | Qwen3.6-35B-A3B — MoE ~3B active, **hybrid attention** (10/40 KV layers) |
| Quant | Q4_K_M (16.8 GB; 17.1 GB MTP — multi-token prediction — variant) | UD-Q4_K_M (~22 GB) |
| Port | 8080 | 8081 |
| Context | **32K per slot, hard cap** | per-slot: `chunk_size + overhead` (40K default) → `-np 8 -c 327680 --no-kv-unified` |
| Parallel | `--parallel 1` — 2nd slot reserved for Q3 self-calls only (mechanics below the table) | `--parallel 8` (continuous batching is default-on; keep `--cont-batching` for explicitness) |
| KV cache | q8_0 K+V, `-fa on` pinned | q8_0 K+V, `-fa on` pinned |
| Backend | Vulkan (Linux: Mesa RADV; Windows: AMD proprietary driver) — decode-bound role | ROCm/HIP + flash attention (prefill-bound role; flags per §7) |
| Variant | MTP GGUF — adopt only per the R4 criteria (§10) | standard |
| Role | plan, write REPL code, decide sub-calls, emit final | chunk-level extraction/summary/QA |

Quantized V-cache hard-requires flash attention; `-fa on` is pinned (not `auto`) so a failed FA probe fails loudly at startup instead of silently changing memory and performance behavior. Whether q8_0 KV actually engages on this hybrid architecture is an S0 check (bf16 KV is the fallback). Root 2nd-slot mechanics: enabling it requires `-c 65536` (llama-server splits `-c` across slots) plus re-priced KV, and is incompatible with the MTP variant, which is single-slot. The physical batch flags `-ub`/`-b` are pinned per server, recorded in `config_snapshot`, and stated next to every S0 number — they shape the concurrency-scaling and contention measurements, and a silent upstream default change (R11) must not move the baseline.

**Startup handshake** (scaffold entrypoint, ahead of C4): before accepting any task, the scaffold queries each server's `/props` and asserts model path, `n_ctx`, `n_parallel`, and cache types against `config.yaml`; any mismatch refuses to start. The `/props` responses (including server build) are recorded into `config_snapshot` (§6). The same assertion re-runs per episode at the C5 quiesce point — a server that crashed and relaunched with different flags mid-benchmark must be caught before it poisons a multi-hour run, not after.

**Why the root gets only 32K:** the root never sees the raw context (I2). It sees truncated prints and sub-call results. A large root window is wasted KV and slower prefill for zero benefit. If the root "needs" more context, that is a scaffold smell — the work belongs in the REPL or in leaves. The cap is enforced, not assumed: the root server runs with context shift disabled, C5 tracks the root conversation from server-reported usage, and crossing 90% of the window ends the episode deterministically as `context_exhausted` (§6). A multi-turn flail loop can fill 32K well inside the wall clock; overflow must be an outcome, never an accident.

**Chunk size is the parallelism lever.** Leaf slots are sized to the chunk budget, not to the model's 262K native maximum. Corrected for the hybrid architecture (only 10/40 leaf layers carry per-token KV): a 32K chunk costs ≈0.35 GB of KV at q8_0; the configured 40K slot (chunk + overhead) ≈0.45 GB, so 8 slots ≈ 3.5 GB versus ≈22 GB for 8 full-window slots (~12 vs ~90 GB on a classic all-layers-KV model). On this architecture KV memory alone no longer forces chunk-sizing — the binding rationale is per-call prefill latency and scheduling: a slot holding one chunk turns around in one chunk-prefill time, keeps the fan-out tail short, and makes per-call cost uniform. **Pre-registered S0 expectation: ≈0.45 GB per configured 40K slot (≈0.35 GB of that is the 32K chunk). A measurement near 1.5 GB/slot signals misconfiguration (dense-sized allocation, or KV quantization not engaging on the hybrid arch) — not confirmation.**

**Memory budget (128 GB total):**

| Item | GB |
|---|---|
| Root weights (Q4_K_M; 17.1 with MTP head) | 17 |
| Leaf weights (UD-Q4_K_M) | 22 |
| Leaf KV (8 × 40K slots, q8_0, 10/40 KV layers) + recurrent state | ~4 |
| Root KV (32K q8_0, 16/64 KV layers ≈ 1.1) + runtime buffers | ~3 |
| OS + scaffold + DuckDB | ~8 |
| **Committed** | **~54** |
| **Headroom** | **~74** |

**KV-per-slot arithmetic INVALIDATED for high slot counts (v0.2.6).** The "≈0.34 GiB/slot" figure below assumed KV dominates. It does not once slots are many: on this hybrid architecture the **recurrent state is per-slot and context-INDEPENDENT**, so slot COUNT prices it, not token budget — estimated 30 Gated-DeltaNet layers × `ssm.inner_size` 4096 × `ssm.state_size` 128 × 4 B ≈ **63 MB/slot in f32** (~31 MB at f16). 8 slots ≈ 0.5 GB; **128 slots ≈ 8.1 GB**, taking the leaf from S0's measured 27.3 GiB to ~35 GiB and dual-residency from 44.0 to ~52 GiB inside the 64 GiB carve. That fits but spends more than half the measured headroom, and it is **arithmetic, not a measurement — measure it before pinning `-np 128` (R13's mitigation)**. Fallback if it does not fit: `-np 64` (5,120 tok/slot, 4 restarts per 200K corpus instead of 2, +13.5 s) halves the state bill.

S0 measured residency (Windows VGM, 64 GiB dedicated carve): leaf §4 topology 27.3 GiB (weights + 2.73 GiB KV/state/buffers ≈ 0.34 GiB/slot), root 16.7 GiB — **dual-resident 44.0 GiB, ~20 GiB carve headroom**; B1 256K single-slot KV+buffers 1.52 GiB (s0/RESULTS.md items 4/7).

Headroom is deliberate. It exists for: (a) a third resident server if S6 ever needs one, (b) A/B running a candidate model next to the incumbent during S5 swaps, (c) larger chunk experiments, (d) B1/B3's dedicated 256K single-slot profile (§8; ~2.8 GB KV, run non-concurrently anyway). Do not spend it by default.

**Host config (Linux path — see A2):** BIOS UMA carve-out at 512 MB; GTT raised via `ttm.pages_limit` / `ttm.page_pool_size` (~100 GiB; `amdgpu.gttsize` is deprecated on kernels ≥ 6.18); `--no-mmap` on both servers so weights land in GTT predictably.

**GEOMETRY LANDED (v0.3.0, 2026-08-14): `scaffold.chunk` ships `size_tokens: 640`, `stride_tokens: 480`, `overhead_tokens: 1920`, and `max_subcalls` rises 522 → 926.** The two blockers §7 #2 raised are both discharged — the 4.4× occupancy effect is a default-flag pathology that does not discriminate between geometries (`s2/OCCUPANCY.md`), and `timings.cache_n` is sound (`s2/CACHE-INSTRUMENT.md`). The cost is re-priced honestly in §7 #2: free in *chunk* tokens, **+25% in served tokens and ~+33% in wall**, because the 311-token head and the 516-token re-query rollback are window-independent and 58% more windows pay 58% more of them. It is landed anyway, because at 1,024 the leaf cannot see the instructions it is being graded against and the cheaper geometry buys answers R5 says are no evidence of anything.

**INSTRUCTION DECAY — CONFIRMED, AND IT UNIFIES TWO EARLIER FINDINGS (v0.2.9, 2026-08-14). The layout is NOT the fix; the window size is.**
Replication was exact (30/30 false positives at 1,024 vs 0/21 at 640, p = 8.74e-15). The confound is dead: at **matched density** (3 entity bindings at every size, larger chunks padded with entity-free filler, asserted at build time) the false-positive rate goes **0/12 at 640 → 12/12 at 1,024** (p = 7.4e-07) → 12/12 at 2,048, while **density at fixed size does nothing — three separate contrasts at p = 1.0**.
**The mechanism, with zero free parameters.** In the shipped layout the instruction-to-generation distance is (window + question) ≈ **685 / 1,069 / 2,093** tokens at 640 / 1,024 / 2,048. §7 #2's independently measured *fact*-cliff bracket is **[967 pass, 1022 fail]**. 685 sits inside the horizon → instructions obeyed → 0/24 false positives. **1,069 sits 47 tokens past the measured fail point → instructions ignored → 24/24.** So the shipped `window: 1024` failed at 100% rather than partially because it puts the system prefix a few dozen tokens on the wrong side of a cliff that was measured for facts, in a different experiment, before this one was designed. The same single horizon predicts all 8 admissible layout×size cells.
**One horizon, two distances: instruction distance sets the answer/refuse CRITERION; needle distance sets RETRIEVABILITY.** The paraphrase column separates them cleanly — moving instructions close (arms B/C) pushes the *chunk* further away, and recall collapses to MISS (not confabulation) even though the needle is well inside the horizon.
**Layout is therefore NOT the lever, and no layout ships.** Arms B (prefix repeated after the chunk) and C (prefix only after the chunk) cut false positives to ~2% but trade them for misses roughly 1:1 (recall 83% → 57% / 65%; MISS 9% → 40% / 32%), and C at 2,048 refuses *everything* (0 false positives, 0 recall) — recorded as a failure, not a success. **At 640 all three layouts are identical (0/24 false positives, 24/24 literal recall).** Layout B's advertised advantage is measured worth **zero**: under R13's never-reuse policy every window lands on a virgin slot and median cold `tokens_cached` is 0.0 in all three arms, while the intra-window re-query that actually pays survives in every layout (warm prefill 54.3 / 53.2 / 49.9 ms). B also costs +305 tokens per call and hits a hard capacity stop at 2,048-token windows. **If budget ever forces the window back to 1,024, reach for C (0 extra tokens), never B.**
*Superseded hypothesis text follows, retained because the reasoning that motivated the experiment is part of the record.*
**(v0.2.8, superseded) The layout below may be optimizing the wrong thing.** The refusal A/B produced an unplanned result with a larger claim than the experiment it came from: the **same** `leaf-prefix.v1.md`, unchanged, produces a 30/30 false-positive rate at a 1,024-token window and **0/21 at a 640-token window** (p = 8.7e-15) — at the short window the leaf emits a clean `NONE`. The natural reading is that **instructions decay with distance from generation exactly as facts do**, and this layout puts the system prefix at the maximum possible distance. That would make the §7 #2 distance cliff (facts beyond ~1,000 tokens become unfindable) and the 95% false-positive rate (instructions beyond ~1,000 tokens stop being obeyed) **the same phenomenon measured twice**, which is a materially different diagnosis from "the leaf is a poor extractor". It also means the sweep's "flat across every size" was flat only across the sizes it measured — the range started at 1,024, above the transition.
The tension this creates is real and unresolved: question-last exists to keep the cached prefix intact, and that bought a measured 20–40× on warm re-query — but at the 1K windows the geometry now forces, the warm lever shrinks to 0.72 s per call, so the cache argument for prefix-first is far weaker than when it was written. **Do not change the layout on this evidence yet:** the effect is confounded with distractor density (a 640-token cell has fewer competing entities than a 1,024-token one), and swapping the layout would invalidate every cache measurement taken so far. Pre-registered follow-up, ahead of the S2 freeze: hold distractor density constant while varying only prefix-to-generation distance, and separately A/B prefix-first against instructions-repeated-after-the-chunk, scoring false-positive rate against `tokens_cached`. That single experiment decides whether §4's central layout choice survives.

**Prefix & cache contract (critical):** all leaf calls share one **byte-identical** system prefix. No timestamps, run IDs, task IDs, or counters anywhere in the prefix — run metadata travels in the trailing user segment or stays out-of-band in the trace. Prompt layout is fixed: `[system prefix][chunk][question]` — question **last**, so a re-queried chunk extends the cached prefix instead of invalidating it at token 0. Reuse mechanics (llama.cpp), **corrected v0.3.0 — the previous sentence here was false on b10375.** It read "the prompt cache is per-slot — there is no cross-slot sharing". It is not: the build ships a **host prompt cache** (`--cache-idle-slots` on by default, `--cache-ram` 8192 MiB) that saves idle slot states to host RAM and restores them **onto a different slot** — measured reusing 958 tokens of a document last served on another slot, against 3 tokens shared with what that slot itself held (`s2/CACHE-INSTRUMENT.md` §2a). It becomes per-slot only with **`--cache-ram 0`** (or `--no-cache-idle-slots`), which `config.yaml` now pins on the leaf for two independent measured reasons: it removes 272 s of a 543 s run (§7 #2's occupancy finding) *and* it is the precondition that makes every token-weighted gate a reproducible function of the prompts rather than of run history. Within a slot, **reuse is quantised to ONE rollback point at `N_resident − ub − 4`** — 516 tokens at the pinned `-ub 512`, measured 132 at `-ub 128` — so a divergence reuses that much or nothing at all, however long the true shared prefix is. Slot routing is longest-common-prefix (`--slot-prompt-similarity`), and `slot_id` is recorded per call (§6) to verify affinity. The monitored metric is **token-weighted** (`steps.tokens_cached`, from the server's `timings.cache_n`), never a boolean — see §7 #3 for the re-derived gates and the structural ceiling on unique-chunk calls. R8 applies: the hybrid Gated-DeltaNet architecture reuses cache through context checkpoints, with documented llama.cpp regressions — cache behavior is verified in S0, not assumed, **on both servers**: the root is the same hybrid architecture, and its turn-by-turn conversation growth is exactly the checkpoint-extend pattern the R8 issues describe (§7 #3c).

## 5. Scaffold Components (Capa 1)

Six numbered components — each lists what it must NOT do; those are the load-bearing lines — plus the section-level contracts that bind them (bridge, registry, dry-run, config schema, CLI, logging, testing). Python 3.12+ (assumption A1, §12).

**C1 — SandboxManager.** Spawns one isolated Python interpreter per episode (§6: one run of a task; raw `CreateProcessW` + Job Object resource limits: CPU time, memory, active-process count) inside a fresh per-episode **AppContainer** (Windows path, decided A2). Persistent across REPL turns within an episode (Jupyter-like: variables survive). Killed unconditionally at episode end or budget breach.
*Must not:* share state between episodes; grant network unless the task config explicitly enables it.

**"No network" restated as an enforceable rule (v0.2.3, replacing "no AF_INET/AF_INET6"):** taken literally the old wording is unsatisfiable on Windows and the implementation violated it on every episode — constructing any asyncio loop opens an AF_INET self-connected loopback pair (measured: self-pipe on 127.0.0.1, inside the AppContainer). The rule is therefore: **no egress.** The sandbox may hold exactly one self-connected 127.0.0.1 socket pair with both endpoints owned by its own pid (asyncio's self-pipe, unavoidable on Windows) and zero other endpoints. Measured enforcement: external egress → `WSAEACCES 10013`; DNS → `gaierror 11001`; **cross-process loopback → timeout, so the sandbox cannot reach llama-server on 8080/8081** (an I1 win, not merely a security one); raw `ws2_32` FFI → blocked by the kernel token. Auditable with one `Get-NetTCPConnection` query against `episodes.sandbox_pid`, precisely because the C1/C4 bridge is a pipe and not a socket — that check belongs in the S3 gate.

**Enforcement layering, stated honestly (v0.2.3).** The kernel boundary is the AppContainer token plus the Job Object's `ACTIVE_PROCESS` limit of 1. Everything inside the interpreter — the PEP 578 audit hook, the shadowed `asyncio` loop constructors, the decoy `__main__`, the re-injected reserved names — **raises the bar; it is not a boundary.** Measured: a frame walk (`sys._getframe`, `asyncio.current_task()`) or `importlib.reload` still reaches the child's own namespace from cell code, and an audit hook covering only `socket.*` was defeated via `ctypes.WinDLL('ws2_32')` until the deny-set was widened to `ctypes.dlopen`/`dlsym`/`call_function` and `subprocess`/`os.exec*`. Scaffold code must never claim otherwise in comments or docstrings. The I1 guarantees that actually hold do so because the things the model could subvert (truncation caps, budgets, routing, termination) **execute scaffold-side, in a different process**, not because the sandbox is escape-proof.

**Known limitation — per-cell output capture is not thread-safe (v0.2.3).** Capture is installed at the `sys.stdout`/`sys.stderr` object level for the duration of a cell. Model code that starts a background thread will have that thread's output attributed to whichever cell happens to be executing when it writes (reproduced deterministically). This is intrinsic to object-level capture and is accepted: fd-level capture would fix attribution but would admit non-UTF-8 bytes, breaking the ASCII-JSON bridge framing and the trace store's text columns. Recorded so it is not rediscovered as a bug.

**C2 — ContextLoader.** Materializes the input as variable `context` inside the sandbox before the root's first turn. Handles str, bytes, file paths, and lists of documents. Also owns the **deterministic chunker**: `chunks = split(context)` (chunk size from config, measured in target-leaf tokens via the leaf server's `/tokenize`), injected read-only into the sandbox. **Cut rule:** fixed target size from config, cut point snapped to the nearest paragraph/newline/code-block boundary within a ±10% token tolerance, deterministic tie-break (earliest boundary). The rule is identical across the §7 #2 sweep (the sweep varies target size only); snap ships on/off behind one config flag and is A/B'd on a non-benchmark fixture before the S2 freeze. Full content-adaptive sizing is rejected (§11). The root chunks **only** via this utility — free-form chunking in model code would make `chunk_size` advisory (a soft I1 violation) and render the §7 #2 sweep uncontrolled. B2 and B3 (§8) use the same chunker verbatim.
*Must not:* place any part of the raw context into any message array (I2); allow model code to redefine or bypass the chunker.

**C3 — OutputTruncator.** Hard cap on all REPL output returned to the root (default 2,000 chars, config). `observation_view` is the ordered, labeled concatenation of stdout, stderr, last-expression repr, and formatted traceback, truncated **as one unit**. Appends a marker: `[truncated: showing 2000 of 184,203 chars]`.
*Must not:* be overridable by model output or by code running in the sandbox (I1). The cap is applied scaffold-side, after execution.

**C4 — LLMDispatcher.** Exposes `await llm_query(prompt, role="leaf")` inside the sandbox. Routes by role to the correct server. Owns an `asyncio.Semaphore` equal to the target server's `--parallel`. **Pre-flight check:** token count via the target server's `/tokenize`; prompts exceeding slot capacity are rejected without dispatch and logged as steps with `status=rejected`. **Retries:** every attempt is a logged step (shared `call_id`, incrementing `retry_idx`, per-attempt `status`); a retried call counts **once** against `max_subcalls`; every attempt's tokens count against `max_total_tokens`. Defaults (config): max_attempts 3, backoff 1 s / 4 s, per-call timeout 240 s. Requests are streamed so that cancellation (client disconnect) aborts server-side generation. **Server death:** retries exhausting against a dead/unreachable server → step `status=error` → episode `outcome=error, outcome_reason=server_unreachable`; **the scaffold never restarts a FAILED server mid-episode** — that would mask the fault the trace exists to record.
**Slot-pool rotation is NOT a restart in that sense (v0.2.6 ruling, forced by R13).** R13's mitigation requires a never-reused slot per window, so a pool of `--parallel` slots is consumed at one per window; a 200K corpus at the shipped window 640 / stride 480 needs **424 windows** (261 at the 1024/768 geometry this ruling was written against) versus a pool of 8. Without rotation the mitigation is inert — every real episode dies at window 9 — and the alternatives are worse: a pool large enough to never exhaust does not exist (128 slots still falls short of 424), and one process per window costs 4.9×. The distinction that keeps the original rule intact is **planned versus reactive**: rotating a healthy server on a deterministic, scaffold-owned schedule is a resource-lifecycle operation, whereas relaunching a server that just failed hides a fault. Rotation is therefore permitted under four conditions, all of which make it auditable rather than silent: it fires only on pool exhaustion (never on an error), it quiesces in-flight calls and re-runs §4's `/props` handshake before resuming, it is logged as a lifecycle event and stamped on the affected step, and its wall-clock is included in the episode's measured time (**3 rotations ≈ 20 s** per 200K corpus at 640/480, up from 2 ≈ 13.4 s at 1024/768 — it must not be excluded the way §8 excludes between-arm relaunch). **A rotation discards every warm slot**, so both questions about a window must be asked before that window's slot is retired — which the dispatcher already guarantees by keeping intra-window re-queries on the window's own slot. Returns the result as a Python object in the caller's REPL — never auto-injected into the root's messages.
**Slot discipline (v0.2.6, R13).** C4 owns slot assignment: one never-reused slot per window, drawn from a pool sized by `--parallel`, with a server restart when the pool exhausts. **C4 must ASSERT the `slot_id` the server returns equals the one requested** — an out-of-range `id_slot` is silently reassigned with HTTP 200 (measured: asked 200, got 72), so a scaffold that trusts its own request believes it has a virgin slot while sharing a used one. C4 also runs R13's foreign-string detector on every leaf answer and records the hit on the step.
*Must not:* let the model choose servers, ports, or semaphore size; exceed `--parallel` (queueing upstream hides latency pathologies from the trace); reuse a slot across windows (R13).

**The C1/C4 bridge.** `llm_query` is a scaffold-injected stub, not importable library code: it serializes requests over a scaffold-owned AF_UNIX socketpair (Linux; duplex pipe on Windows) passed at spawn — the only channel crossing the sandbox boundary, and explicitly exempt from the no-network rule (which bans AF_INET/AF_INET6, not the scaffold's own pipe). Semaphore, routing, retries, timeouts, and step logging all execute **scaffold-side**; nothing the model runs in the sandbox can alter them (I1). The sandbox REPL compiles cells with top-level `await` against a persistent event loop so `await llm_query(...)` is natural. **The name `llm_query` is load-bearing:** it matches the RLM paper harness API (alexzhang13/rlm) that RLM-post-trained roots are conditioned on (S5 candidate track) — do not rename casually.

**C5 — BudgetEnforcer.** Per-episode limits from config. Termination is deterministic and unconditional.
*Budgets:* `max_depth` (default **1** — root + leaves, no grandchildren); `max_subcalls` (default 32); `max_wall_clock` (default 15 min; re-derived per task-size class after S0: ≈2–3× predicted prefill time at measured t/s); `max_total_tokens` (default 1.5M); `max_predict` per call, **per role** (root 1024; leaf 512 default, re-derived from the S1 answer-length distribution — a 1024-token reservation against ~100-token extraction answers inflates admission accounting by up to ~30K phantom tokens across 32 subcalls).
*Root window:* accounting from server-reported usage per turn; at ≥90% of the root window the episode terminates deterministically as `context_exhausted`.
*Admission:* the token budget is enforced at dispatch admission — `running_total + reservation ≤ cap`, reservation = pre-flight prompt tokens + role `max_predict`; worst-case overshoot is bounded by in-flight calls × `max_predict` and documented.
*On breach:* cancel all in-flight dispatcher tasks (closing streamed connections aborts server-side work), release the semaphore, kill the sandbox, mark the outcome, persist partial state and full trace; cancelled calls are logged as steps with `status=cancelled`. Operator Ctrl-C routes through this same path (`outcome_reason=operator_abort`) — never dies mid-write.
*Quiesce:* between timed episodes the scaffold verifies both servers report all slots idle before starting the clock, and re-runs the `/props` assertion (§4).
*Must not:* warn-and-continue; accept model requests for extensions. Raising `max_depth` above 1 requires S4 evidence that depth-1 is the binding constraint.

**C6 — TraceLogger.** Single writer task fed by an asyncio queue; **one transaction commit per step** — this is what "a crash loses at most the current step" means — with blobs written before their referencing row. `step_idx` is assigned in commit order; causality is carried by `parent_step_idx`/`call_id`, never by `step_idx` adjacency. Blobs go to a per-episode directory, referenced by episode-relative paths. Monitoring reads happen in-process (DuckDB is single-writer; external readers get an append-only export, not a live handle).
*Must not:* sample, summarize, or truncate the stored record (store full observation as a blob ref; only the *root's view* is truncated, per C3).

**Lifecycle log (narrow, and not a second truth).** Operator logs are forbidden as a channel for episode data — the trace store is the sole episode record (I4). One JSONL lifecycle log (stderr + file) exists for exactly the events the trace store structurally cannot record: its own write failures, config-validation refusals, startup/per-episode handshake refusals, server health transitions, quiesce waits, and recovery actions at restart. Nothing else. The S3 reconstructability gate runs with this log deleted, so two-sources-of-truth drift is structurally impossible.

**Prompt registry.** Root and leaf system prompts live as files under `prompts/` with monotonically versioned names (`root.v3.md`), referenced from config by path and pinned by sha256; inline prompt strings in config or scaffold code are forbidden. Each file opens with a one-line-per-version changelog header. **Strategy templates:** a config-owned library of five strategy blocks (needle: scan-with-code-then-leaf-verify; aggregation: full-coverage map over `chunks` with code-side reduction; synthesis: per-document leaf briefs then cited merge; code-QA; plus a generic default for ad-hoc tasks). The task's **declared category selects the block deterministically — the model never chooses** (I1). Adversarial-context tasks (§8) declare the category of their underlying shape — the injection lives in the corpus, not the category; R12 hardening (the evidence-span check) lives in all extraction-shaped templates. The selected template is appended to the root system prompt; its sha256 goes into `config_snapshot`. Templates for extraction-shaped categories include the evidence-span check (R5) and a REPL-prescan tip (regex/keyword scan of `context` before spending leaf calls — the paper's models did this unprompted). Authoring happens in S1 against non-benchmark fixtures; the library freezes at the end of S2 together with the benchmark, under the same no-overfit rule. Rationale: the strongest verified no-training lever against R1 — Prime Intellect showed a strategy hint flips harness results for untrained models, and minRLM's code-first scaffold (§13; self-reported, no component ablation) is directionally consistent: +22.3pp for a mini-class untrained model, −9.5pp for a nano-class one that cannot write reliable code.

**Dry-run mode.** `dispatcher: mock` in config runs a full episode with canned responses from a fixtures file keyed by (role, prompt-hash) — real sandbox, real C1/C2/C3/C5/C6. Episodes in this mode carry `dry_run=true` (§6) and `config_snapshot.dispatcher="mock"`; the bench runner and every scoring query refuse dry-run rows, keeping I7 airtight. The mock is canned-response-only — any "leaf simulation" realism would drift into I3 territory.

**Config schema.** `config.yaml` is a pydantic model with `extra="forbid"` (a typo'd `max_subcals:` silently running at defaults is an I1-grade hazard) and cross-field validators encoding the §4/§5 arithmetic: leaf slot ctx ≥ chunk_size + overhead; root `-c` == root window; C4 semaphore ≤ leaf `--parallel`; reservation ≤ slot capacity; MTP variant ⇒ root single-slot. **CORRECTION (v0.2.6): "C4 semaphore == leaf `--parallel`" is decoupled to `≤`.** The equality was right while `--parallel` meant "calls this server serves at once". Under R13's never-reuse policy `--parallel` sizes the slot POOL — how many *windows* one leaf process serves before rotation — and is derived from the measured per-slot memory bill (62.8125 MiB of recurrent state per slot, `s2/R13-slotcount.md`), while dispatch concurrency remains a throughput lever measured against S0's flat aggregate prefill. At the pinned `-np 128` the equality would put 128 leaf calls in flight at once for a reason that is purely about memory. The inequality preserves what the equality protected: every in-flight call holds one slot, so concurrency may never exceed the pool. `config_snapshot` is the canonical JSON dump of the validated model (stable field order ⇒ stable hashing). Sketch: Appendix A.

**Operator surface (CLI).** The only entrypoint, five verbs: `rlm validate` (config schema + `/props` probe), `rlm run <task-file>` (one episode; prints episode_id + outcome), `rlm replay <episode-id>` (§6 replay check + transcript render), `rlm bench --arm {rlm,b1,b2,b3} --seeds 1,2,3` (the frozen §8 protocol, including blocked scheduling and quiesce), `rlm export <run-id>` (run-id = one `rlm bench` invocation, stamped into every episode's `config_snapshot`; a single episode-id is also accepted; self-contained bundle: parquet export + blob directory + config snapshots — the external-reader export C6 promises, and the concrete mechanism behind R1's publish-a-negative-result commitment). **Non-goals, written down:** no daemon, no REST API, no web UI, no interactive chat mode.

**Dependency rule (lint-enforced, same pattern as Conduo — external reference, §12):** C1–C3, C5, C6 must not import C4 or any LLM client. Only C4 talks to model servers. The scaffold must be able to run a full episode with a mock dispatcher (used in S3's runaway test). **Composition-root exemption (v0.2.3):** exactly two modules may import both C4 and the isolated components — `rlm/episode.py` (which wires an episode) and `rlm/cli.py` (which wires the process: `validate`'s server probe, dispatcher construction, and crash recovery all need both sides). The lint exempts both **by name**; adding a third name to that list is a spec change, not a refactor.

**Testing:** every C-component ships unit tests against the mock dispatcher (pytest, A1); each slice gate additionally requires the component suite green. **Property-based suites (hypothesis) are mandatory for the two components that carry I1/I2:** C3 — over arbitrary (stdout, stderr, repr, traceback) tuples including pathological unicode, NULs, and megabyte single lines: view ≤ cap always, truncation applied to the concatenated unit (never per-stream), marker counts accurate and the marker itself never truncated, deterministic; C5 — a stateful machine driving the mock dispatcher through arbitrary interleavings of dispatch/complete/retry/cancel/breach, with invariants: admitted reservations never exceed the cap, overshoot ≤ in-flight × max_predict, no admissions after breach, termination always reached, a retried call counts once against `max_subcalls` while every attempt's tokens count against `max_total_tokens`. Hypothesis profiles/seeds pinned in CI.

## 6. Data Layer — Trajectory Schema

The one decision made today that pays later: traces are stored **trajectory-shaped**, not log-shaped. The tuple `(state, action, observation, outcome)` is simultaneously the SFT format of the original RLM paper, the training format of Qwen-AgentWorld, and the raw material for a Voyager-style skill library. Zero runtime cost; three learning paths kept open.

**The state rule (discharges I4):** "state" is not a column. Root state at step *k* := deterministic replay of steps 0..*k−1*'s `(action, observation_view)` under the versioned system prompt (prompt registry, §5). The schema stores everything that replay needs — nothing else is required. **The rule has an instrument:** `steps.root_view_hash` stores, for every root turn, the sha256 of the exact chat-template-rendered request sent to the root server (canonical serialization pinned — the rendered string, not the message list). `rlm replay` re-derives the message array at every step from the trace alone, recomputes the hash, and asserts equality; this is the S3 gate check and the standing regression canary for prompt-assembly drift.

**The final-answer channel:** `final` is emitted only via the scaffold-injected `final_answer(value)` inside the sandbox — never parsed from root prose. (A prose-parsed answer would be the one channel able to smuggle untruncated context past C3, violating I2.) The value is stored to a blob; the call is the episode's terminal step.

**Terminology:** episode = one run of a task; `task_id` is stable across seeds and arms; `task_hash` = sha256 of the instruction text (corpus documents hashed separately, in the benchmark manifest referenced by `benchmark_version`).

**`episodes`**

## 7. Performance Model & Optimization Order (Capa 2)

**Numbers below are on-box S0 measurements (2026-08-13; llama.cpp b10375, `-ub 512 -b 2048`, q8_0 KV, FA on; protocol, raw per-run records, and addenda: `s0/RESULTS.md` + `s0/results/raw.jsonl`). The community priors they replaced are preserved in git history (≤ v0.2.2).**

Decode ceiling (bandwidth-bound): `t/s ≈ BW_eff ÷ (active_params × bytes/param)`, with BW_eff ≈ 212 GB/s measured (256 theoretical).
- Root (27B dense-FFN, Q4): theoretical ceiling ~15 t/s. Measured: **12.35 t/s fresh, 12.0 at 28K depth** (Vulkan; ROCm A/B 12.41 / 11.05). **Contended — during a verified full 8-slot leaf prefill: 8.5–10.0 t/s (69–81% retained).** Acceptable: root emits code, not prose.
- Leaf (~3B active, Q4): measured single-stream **55.1 t/s fresh, 46.3 at 32K depth**; at 200K depth (B1 profile): 18.2. Aggregate decode across 8 continuous-batching streams: **143 t/s** (8 × 20.3, uniform; 2.6× single-stream).

Prefill is compute-bound and is the real budget: a 32K-token leaf chunk is the unit cost of everything (**34.6 s single-slot on-box**). Measured leaf prefill at d=32K (median of 3 cold runs, single slot): **949.9 t/s ROCm / 836.2 t/s Vulkan** — Windows on-box beats the Linux community priors (807/716). **S0 finding: aggregate prefill is FLAT at ~950 t/s for k=1/2/4/8 concurrent 32K streams — a single stream already saturates the iGPU. Fan-out buys scheduling and decode overlap, never aggregate prefill throughput.** B1 full-window reference: a 200K-token prefill averages 320 t/s (depth decay), ≈10.4 min per pass — the depth-decay gap (947 vs 320 effective) is the RLM arm's structural wall-clock advantage over single-pass long context on this hardware.

**Contention model (measured):** root decode and leaf prefill share one iGPU. S0 measured the contended case — root decode during a verified active 8-slot leaf prefill retains **69–81%** of uncontended speed (8.5–10.0 vs 12.35 t/s). Concurrent operation is viable; phase alternation is an optimization, not a correctness requirement. The R4/MTP comparison must state its contention condition.

**Backend split: chosen and pinned at S0 (on-box A/B, 2026-08-13).** Leaf on **ROCm/HIP** (prefill-bound role): +13.6% prefill vs AMD-proprietary Vulkan at d=32K (949.9 vs 836.2 — same direction and size as the Linux prior). Root on **Vulkan** (decode-bound role): fresh decode ties ROCm (12.35 vs 12.41), but Vulkan holds decode at depth (+8.6%: 12.0 vs 11.05 at 28K); ROCm's +39% root prefill (290 vs 208) does not outweigh the decode-bound role. Windows runtime recipe: ggml-org win-rocm zip + AMD ROCm 7.14.0 wheel DLLs (hipblas/rocblas/rocsolver/hipblaslt + gfx1151 Tensile/kpack) beside llama-server.exe; runtime `ROCBLAS_USE_HIPBLASLT=1`. Flag caveat (v0.1.1) retained for the record: rocWMMA FA was reported slower than plain HIP FA at long context since ROCm 7.0.2+ — the ggml-org build ships rocWMMA FATTN=ON and still posted every number above; FA-path variants stay parked in #5.

Optimizations in strict order of expected return. Per I5, each ships only with benchmark-neutral-or-better evidence, and each has one owning metric:

1. **Parallel dispatch — DEMOTED TO LAST AND CURRENTLY FORBIDDEN (v0.3.1, R14).** This was ranked first on the assumption that fan-out is a free scheduling win. It is not: measured serial 31/32 correct against 9–10/32 at two calls in flight, and fan-out at that level buys 13% of wall-clock while costing 68% of the answers. `dispatch_concurrency` ships at **1**. Do not measure a speedup that is paid for in correctness — if the `--no-cont-batching` lead identifies continuous batching as the cause and an upstream fix lands, this entry returns to the list *and must then be re-measured on correct-answers-per-second, never on wall-clock alone*. Original entry retained below for the record.
   *(superseded)* metric: measured speedup on the 8-leaf fan-out fixture vs serial. Target: **≥80% of the aggregate prefill scaling S0 measures at 8 slots.** *S0 resolved this: aggregate prefill is flat (946.7 t/s at 8 slots ≈ batch-1's 943.4) — there is no multiplication to harvest; the S2 gate (c) target is an effective 8-chunk wave rate ≥758 t/s, and this optimization's value is scheduling, latency-hiding, and decode/prefill overlap under continuous batching.*
2. **Chunk-size tuning** — **PROMOTED TO FIRST, AND GIVEN A QUALITY AXIS (v0.2.4, 2026-08-13).** The S2 leaf-transport fix made the leaf path work for the first time, and measuring it immediately falsified the 32K default. On the real leaf (Qwen3.6-35B-A3B, 21 live calls) against a chunk that provably CONTAINS the needle: at ~550 tokens the leaf returns the exact key, the exact paraphrased entity, and a clean `NONE` for an absent fact; at ~1K and ~10K it returns `NONE`; **at ~30K it returned the true UUID with the final character altered** (`…feb83` for `…feb89`) — deterministic, reproduced byte-for-byte on a serial control, alongside a flat "No" to a phrase literally present in the chunk. That is the worst failure mode available to this architecture: a fluent, correctly-formatted, character-plausible confabulation that a careless root submits and a `contains` checker scores as a miss rather than as a lie. **The leaf works; the leaf at 32,768 tokens does not.** Consequently: the sweep runs BEFORE any other optimization, its primary metric is extraction CORRECTNESS (exact-match plus a confabulation count — a near-miss must be scored separately from a `NONE`, because they have opposite remedies), wall-clock is secondary, and the usable range is bracketed somewhere under 10K on this corpus. Sweep {1K, 2K, 4K, 8K, 16K, 32K} on non-benchmark fixtures.
   *Relationship to the §8 chunk-size lock:* the lock forbids sweeping RLM's main lever on benchmark-adjacent signal. It is not violated here — the benchmark does not exist yet (authoring is an S2 deliverable), and this evidence comes entirely from S1's synthetic non-benchmark corpus. Re-deriving the default BEFORE the benchmark is authored is the opposite of test-set tuning; freezing a benchmark around a chunk size measured to produce confabulation would corrupt S4 outright.
   *Superseded prior text:* wall-clock per task at fixed quality, swept over {16K, 24K, 32K, 48K}.
   **SWEEP RESULT (v0.2.5, 2026-08-13 — the chunk-size question was the wrong question).** 78 fact-present trials across {1K…32K} on a real leaf, one fresh process per cell (see R13). **Retrieval does not degrade with chunk size; it falls off a cliff at absolute DISTANCE from the needle to the question: 38/39 correct within ~1,000 tokens, 0/39 beyond it** (Fisher p ≈ 1e-21). Size is ruled out directly by the data's own counterexamples: a **32,768**-token chunk whose needle sits 967 tokens from the end scores **6/6**, while a **1,024**-token chunk whose needle sits 1,022 tokens from the end scores **0/3**. Relative depth is ruled out too (depth-50% works at 1K and 2K, fails at 4K+). The measured bracket is [967 pass, 1022 fail].
   **GEOMETRY LANDED (v0.3.0, 2026-08-14): `size_tokens: 640`, `stride_tokens: 480`, `overhead_tokens: 1920`, `max_subcalls: 926`.** Both v0.2.9 blockers are discharged (below), and the decision is made on re-measured cost, not on the "free in prefill" claim it was proposed with.
   **The cost claim was half right, and here is the honest version.** Over a 200,000-token corpus, run through the real C2 chunker on fixture prose with the shipped snap:

   | | 1,024 / 768 | 640 / 480 | Δ |
   |---|---|---|---|
   | windows (measured, real chunker¹) | 268 | 424 | +58% |
   | chunk tokens prefilled | 282,475 | 276,826 | **−2.0%** |
   | served prompt tokens (incl. head + re-query) | 515,903 | 646,130 | **+25.2%** |
   | leaf wall, serial, `--cache-ram 0` | ~884 s | ~1,180 s | **+33%** |

   ¹ *`rlm.chunker.split` itself, on 754,540 characters of S2 fixture prose, with a linear char-per-token counter calibrated to the measured 3.7727 — not the leaf's `/tokenize`, which would cost ~20,000 HTTP round trips. The proxy is monotone and linear, so it prices the geometry correctly; the exact window count on a given corpus still moves with real tokenization, which is precisely why `max_subcalls` is set from the snap bound and not from this number.*

   The "identical 1.333 overlap factor ⇒ free" reasoning was true of **chunk** tokens only, where 640/480 is in fact 2.0% *cheaper*. It is false of what the server actually prefills, because two per-call costs are **window-independent**: the 311-token rendered head, and the 516-token (`ub`+4) rollback that every intra-window re-query re-prefills. 58% more windows pay 58% more of both. Decode compounds it — 848 answers instead of 536 at ~0.6 s each.
   **Landed regardless, and the reason is that the cheap geometry buys nothing.** At 1,024 the leaf's own prefix sits past the horizon: 30/30 false positives, and `s2/OCCUPANCY.md` §8 reproduced the recall gap by accident on a corpus built for a different purpose (122/128 correct at 1,024 against 128/128 twice at 640, same prefix, same sampling, same documents). §10 R5 says a leaf answer is no evidence the fact was present; at 640 that stops being true (0/45 false positives, 45/45 literal recall). The +296 s is the price of the leaf answering the question it was asked.
   **Window count is NOT the formula the spec priced it with.** `ceil((T − size)/stride) + 1` assumes every window end lands exactly one stride after the last; C2's `_snap_back` moves ends **backward** to a boundary within the ±10% tolerance, so the shortest gap is `int(stride × 0.9)` and the count rises. Measured 424 against the formula's 417 — and 268 against 261 at the old geometry, which means **the shipped `max_subcalls: 522` was already 14 calls short of its own geometry** and would have truncated coverage silently. `max_subcalls` is therefore derived from the bound no corpus can beat: `2 × ceil(200,000 / 432) = 926`.
   **BLOCKER 1 DISCHARGED — the 4.4× was a default flag, and it never discriminated between geometries (`s2/OCCUPANCY.md`, 1,416 calls, 24 conditions).** All of the growth is `latency_queue_ms`; prefill is flat (1,391 → 1,389 ms across a 3.07× change in wall). Cause: `--cache-idle-slots` saves every idle slot to a host prompt cache on each new task, and `--cache-ram`'s 8,192 MiB default holds **41 entries** of this config's 202.80 MiB slot state against a 128-slot pool — past which evictions per request equal the occupancy **exactly** (0 up to 40, 1 at 41, then N) at 37.5 ms each: 7,268 evictions, 272 s of a 543 s run, predicted mean 4.193 s against a measured 4.233 s with no free parameters. `--cache-ram 0` and `--no-cache-idle-slots` each remove it entirely (flat 2.05–2.16 s at occupancy 0–127) and each cost the warm re-query nothing (50 ms, `cache_n` identical element-for-element). Ruled out with controls: `-sps 0`, pool size (`-np` 8/32/128 at 8 in use: 38/37/37 ms), slot index versus call ordinal (r = 0.960 vs −0.035), httpx limits. **The overhead is priced by the slot pool, not the window** (37.5 ms/slot at 1,024, 38.3 at 640), both geometries drain the same pool to the same ceiling, and at peak occupancy the 640 call is the *cheaper* one (6.35 s vs 6.87 s). `--cache-ram 0` is now pinned in `config.yaml`.
   **BLOCKER 2 DISCHARGED — `timings.cache_n` is honest; the truth model was wrong (`s2/CACHE-INSTRUMENT.md`, 373 calls).** Against the best common prefix with *any* prompt the process served, it over-reported **0/373**. The 1,374-vs-3 anomaly is the host prompt cache restoring an idle slot's state onto another slot, reproducible on demand and removed by either flag. With the flag on, reuse is an exact closed form of two numbers the scaffold already holds — **239/239 calls, 0 tokens of error, at two `-ub` values** — and it is implemented as `rlm.dispatcher.predicted_reuse`. §7 #3's gates are re-derived against it below; the v0.2.9 INSTRUMENT WARNING is **discharged, not carried**.
   **A THIRD BLOCKER, found by the occupancy controls, and it does not block this edit but blocks the next one: concurrent leaf dispatch destroys the answer.** Serial, 31/32 correct; at 2 calls in flight 7/32; at 3, 3/32; at 4, 2/32; at 8, 7/128 — degenerate text (`'###/remainile'`), not wrong answers, with no foreign identifiers, so **R13's detector cannot see it**. Reproduced with two independent OS processes sharing one server, so it is the server and not the async client. `scaffold.dispatch_concurrency: 8` is shipped config and is the value §7 #1 was written around. **The break is at two.** Every wall-clock figure above is therefore a serial one, `max_wall_clock_s` may not be re-derived until this is characterised, and this defect gets R13's treatment — minimal reproducer, mechanism, upstream issue — before any config edit picks a number.
   **Consequence: chunk SIZE is not the lever — window/stride geometry is.** Shipping `size_tokens: 1024` would still leave the head of every chunk outside the horizon. *(v0.2.5's derived recommendation of **window 1024 / stride 768** is SUPERSEDED by the 640/480 landing above — it satisfied the fact horizon and violated the instruction horizon, which v0.2.9 showed is the same horizon. The structural half of the claim stands and shipped: §4/C2 gained an overlap parameter, and `max_subcalls` rises with the geometry or coverage silently breaks.)*
   **The other measured number is worse than the cliff: the leaf's FALSE-POSITIVE rate is 37/39 (95%), flat across every size.** Asked about a fact that is absent, the leaf almost always answers anyway. **A leaf answer is therefore no evidence the fact was present** — which is a statement about the whole architecture's error model, not about chunking.
   **Open gap the sweep must close first (v0.2.4): the layout fix is inert in production.** `llm_query` now accepts `chunk=` so the scaffold composes `[prefix][chunk][question]` itself, and `prompts/root.v2.md`'s exemplars teach it — but **`root.v1.md` is the pinned S1 A/B winner and does not**. The running root therefore still emits the single-string form, `chunk=None` on every call, and the layout stays unenforced exactly as measured. Closing this requires a `root.v3.md` (v1's tips verbatim + the `chunk=` form), pinned for S2 onward; v1/v2 stay untouched so the recorded S1 tie remains a valid historical result. Legitimate now because the prompt registry freezes at the END of S2 alongside the benchmark, and neither exists yet — but it must land before any reuse gate is scored, or gate (b) will measure a root that was never taught the API it is being graded on. Fold the v3 authoring into the chunk-size sweep, whose fixtures are the right place to check that the taught form survives contact with a real root. 3. **Prefix caching** — **ALL THREE GATES RE-DERIVED v0.3.0** against the measured reuse law (`s2/CACHE-INSTRUMENT.md`, 373 calls). The law, implemented as `rlm.dispatcher.predicted_reuse(N, L, ub)` where `N` is the token length of the prompt that last occupied the slot and `L` the longest common token prefix with the incoming one:

   ```
   N − 4               if L ≥ N          # byte-identical re-send
   L                   if L ≥ N − 4      # CONTINUATION: the prompt extends the slot
   N − ub − 4          if L ≥ N − ub − 4 # DIVERGENCE: the single rollback point
   0                   otherwise         # the shared prefix is NOT available, however long
   ```

   Scored against `timings.cache_n` it is **exact on 239/239 calls at `-ub` 512 and 128** (gaps 516 and 132). **Two preconditions, both load-bearing:** `--cache-ram 0` (or `--no-cache-idle-slots`) must be in the launch line, or cross-slot restore adds reuse the model cannot see and `cache_n` stops being a function of the prompts at all (the same call reported 0 or 958 depending on host-cache eviction order); and `ub + 4` is a property of a **build and a flag** (R11), re-measured whenever either changes (`s2/run_cache_instrument.py`, ~4 minutes, is the regression test). `timings.prompt_ms × cold rate` is kept as the **independent** cross-check — median ±17, p95 ±69 tokens — precisely because it does not move when the law does; a divergence beyond 69 tokens is the signal that llama.cpp's rollback behaviour changed. `prompt_n` is **not** a second opinion: `cache_n + prompt_n` equalled the tokenized prompt length on 373/373 calls.
   **(a) Prefix integrity — the R3 drift detector, in two parts.** The original (`tokens_cached ≥ tokenized-prefix-length` on every warm-slot call) is **unmeetable, and now provably so**: it needs the divergence point (311, the end of the prefix) at or after the rollback point, i.e. `N ≤ 315 + ub`, and even there reuse equals `N − ub − 4 ≤ 311` — satisfiable only at the single value `N = 315 + ub`, one token wide, at any `-ub`. Under R13's never-reuse policy production has no warm-slot first-sight call at all (`cache_n` was 0 on 236/236). An assertion that cannot fail is not a detector.
   > **(a1) — always on, zero cost, no model call.** On every leaf and root call, assert `sha256(rendered_system_head) == config_snapshot.prefix_render_sha256` **and** `len(tokenize(head, add_special=True)) == 311`. Fail the episode (`outcome_reason=prefix_drift`) on either. *Measured stable at 311 tokens across 6 server launches and 373 calls; it fails the moment a byte moves, which is exactly and only what R3 is about.*
   > **(a2) — the cache-side residue that CAN fail.** On the intra-window re-query — the only warm call production makes — assert `cache_n == N_resident − ub − 4` **exactly**. *Measured on 42/42 divergences that reused anything, with the other 28/28 correctly reusing nothing. Zero tolerance: the quantity is an integer identity, not an estimate.*

   **(b) Repeated-chunk reuse (the win case).** The old >80% token-reuse target is **reachable and measured to be a net loss**: the ceiling on a re-query is `(N − ub − 4)/N_new`, so 80% needs `N ≥ 5(ub+4)` = 2,580 tokens at `-ub 512` — a chunk outside the horizon §4 permits — while `-ub 128` clears it at the 640 window (85.7% reuse) and costs **+50.2% of prefill per window** (cold throughput 961 → 478 t/s; +336 s over a 424-window corpus). **Keep `-ub 512`; do not buy the 80%.** A reuse *fraction* is not a gate on this stack at all: it is fixed by geometry at `1 − (ub+4)/N` and carries no information about whether caching works. Only the identity does.
   > **(b1) — the assertion.** On every intra-window re-query, `cache_n == N_resident − ub − 4` (identical to a2; one identity serves both intents). *Measured 42/42 exact.*
   > **(b2) — the win, priced honestly.** Median re-query prefill ≤ **0.62 ×** median cold prefill for the same window. *Measured 0.583 (587.1 / 1,006.5 ms) at window 640 — i.e. **1.72×**, saving ~440 ms of wall per re-query.*
   > **(b3) — the contingency trigger.** If (b1) fails on >2% of re-queries in an episode, LCP mis-routing or an R8 checkpoint regression is real and the per-episode `{chunk_hash → slot_id}` map ships. *Currently 0%.* Contingency design, unchanged: C4 keeps the map, re-queries pass `id_slot` explicitly, new chunks take the least-recently-used entry. Caveat, documented: pinning serializes concurrent calls targeting one slot; queue-latency spikes there are expected, not pathological.

   **(c) Root-turn integrity (always on) — measurable, and it passes with equality.** A rendered `[system, user]` prompt is a strict token prefix of the `[system, user, assistant, user']` that follows it, so conversation growth is a **continuation** and never touches the rollback point that costs the leaf its reuse. Measured over four-turn conversations at both host-cache settings and both `-ub` values: `cache_n` equalled the true LCP **exactly on 14/14 turns**, prefill fell 967 → 178 ms (5.4×), `prompt_n` was exactly the new observation. **R8's feared checkpoint invalidation does NOT occur for pure conversation growth on b10375.**
   > **(c) — the assertion.** On every root turn *k* > 0, assert `cache_n == LCP(rendered_turn_k, rendered_turn_{k−1})` **and** `LCP ≥ prior_request_tokens − 4`. Flag the episode on either. *14/14 exact; the −4 is the generation-prompt markup and is an identity, not slack.* Because `root_view_hash` (§6) stores the rendered request per turn, the LCP is computable from the trace alone — the check runs in `rlm replay` as well as live.
   > **Stated limitation:** those turns were served by the **leaf** process (port 8081, ROCm, `-np 128`) because it is the same architecture. §4's "verified on both servers" still requires one pass on the root (port 8080, Vulkan, `-np 1`) before (c) is treated as verified there. The assertion is ready; the root measurement is not taken.
   **(d) Measured on the fixed leaf path (v0.2.4) — and RE-PRICED at the shipped geometry (v0.3.0): the re-query lever is worth 1.72×, NOT 20–40×.** The saving is `ub + 4` tokens of re-prefill regardless of window size, so as a *fraction* it shrinks exactly as the window shrinks; the 20–40× figure below was measured at 30K chunks and does not transfer. Any plan pricing intra-window re-query at the 30K figure is wrong by an order of magnitude. (The 30K measurement itself is corroboration for the law, not a contradiction of it: `N − 516 = 29,641` puts that prompt at 30,157 tokens, exactly where a ~30K chunk plus a 311-token head lands.) Original text: re-querying a resident chunk is the one lever that unambiguously works — a second question against a 30K chunk already in a slot reported `tokens_cached: 29641`, 850 ms prefill, **1.71 s wall versus 35.45 s cold** (an identical repeat: 0.22 s), with `slot_id` stable per chunk. The system prefix landing ahead of the chunk did NOT break affinity. Restate gate (a) conditionally on chunk identity (`tokens_cached >= prefix_len` only when the slot already holds that chunk; for a first-sight chunk the honest assertion is `tokens_cached < prefix_len`, and the interesting number is the cold/warm prefill ratio, measured 16.6×). **RESOLVED (v0.2.5): the `-ub` hypothesis is FALSIFIED — keep `-ub 512`.** The pre-registered experiment ran at both 512 and 128: `cache_n(B) = 0` in BOTH cases against the 311-token prefix, so the ubatch boundary was never the mechanism. `-ub 128` additionally costs ~43% of prefill throughput (1,003→575 t/s at 2.4K; 933→584 t/s at 16.7K) and buys nothing. **Gate (a) is therefore not meetable for a first-sight chunk on this stack, by any configuration.** *(v0.3.0: the conditional restatement proposed here is superseded — a conditional inequality is still unmeetable at every `N ≠ 315 + ub`. ## 8. Measurement (Capa 3)

**Primary metric:** wall-clock per task at fixed quality. Never t/s in isolation (I5).

**Secondary metrics:** leaf prefill t/s; root decode t/s (contended and uncontended); leaf `tokens_cached` ratio; per-episode time split (REPL exec / LLM wait / scaffold overhead) — all derivable from the `steps` table, by design. Package temperature logged per episode (R9).

**Sampling & seeds:** per-role `temperature`, `top_p`, `seed` live in `config.yaml` and are recorded in `config_snapshot`. "3 seeds" = sampling seeds {1, 2, 3} per task per arm. Stated caveat: continuous batching means a fixed seed does not guarantee bitwise reproducibility — seeds pin sampling identity, not numerics.

**Frozen benchmark:** the task count is chosen at freeze by a pre-registered rule and fixed thereafter (the scoring denominator depends on it): **20 tasks by default; 30 tasks (margin scaled to +3) if S0-derived cost projections keep a full S4 (4 arms × 3 seeds × N tasks + escalation reserve) under the wall-budget of 60 h — exact, fixed now, not restated after S0.** Programmatically verifiable (exact match with stated normalization, or checker function). **Authoring is an explicit S2 deliverable:** each task ships as (input ref, question, checker fn, expected answer) with unit-tested checkers and pinned corpus sources (repos at a fixed commit for code QA). Frozen and versioned at the **end of S2**; S2's own gates run on dedicated non-benchmark fixtures so S2 cannot overfit the benchmark it is authoring.

*Contamination & checker-validity preconditions (must pass before freeze):*
1. **Closed-book probe:** every benchmark question runs context-free against both the root and leaf models, 3 seeds each; any task answered correctly in ≥1/3 seeds without the corpus is rewritten or replaced (memorized answers differentially inflate the single-shot arms — B1/B3 lean hardest on parametric knowledge).
2. **Synthetic needles:** needle tasks embed generated facts (random entity–UUID pairings) that cannot exist in any training corpus.
3. **Corpus dating:** pinned commits/documents post-date the models' training cutoff where feasible; the benchmark manifest records each corpus date against the assumed cutoff.
4. **Checker near-miss suite:** each checker's unit tests include ≥3 authored plausible-but-wrong answers that must fail, plus normalization edge cases (permissive checkers convert R5 confabulation into false passes in every arm).

**Corpus-size ceiling per category (v0.2.7, forced by measurement — decide BEFORE authoring, which is why it is written here now). RE-DERIVED v0.3.0 at window 640 / stride 480; the verdict STANDS and the margin is worse.** At the measured 3.7727 chars/token a **1M-char corpus is 265,060 tokens**; at 640/480 that is **552 windows by formula, ≤614 by the snap bound = 1,104–1,228 sub-calls** for full coverage (it was 345 windows / 690 sub-calls at 1,024/768). Against the shipped budgets, `max_subcalls: 926` **breaks first, at ~75% coverage** — almost exactly where 522 broke, because the budget and the requirement scale with the same geometry — and it breaks silently, as partial coverage, in the one category that punishes sampling. Raising it only moves the breach to `max_wall_clock_s: 900`, and that breach **grew from ~955 s to ~1,560 s** with the smaller window. `max_total_tokens: 1.5M` still holds, but its margin halved (~1.17M expected, against 1.02M before). So **full coverage of a 1M-char corpus is not affordable on this hardware** — the conclusion is unchanged, and no budget was raised beyond full 200K-token coverage, because raising sub-calls just relocates the failure.
*Two corrections the re-derivation forces.* (1) **The window-count formula under-counts.** `ceil((T − size)/stride) + 1` assumes maximal gaps; C2's backward snap makes the shortest gap `int(stride × 0.9)`, so every window count in this section is stated as a bound (`ceil(T / 432)`) and not as the formula. The formula's error is what left `max_subcalls: 522` 14 calls short of its own geometry. (2) **Every wall-clock figure in this section is a SERIAL one.** `s2/OCCUPANCY.md` §7 measured concurrent leaf dispatch corrupting answers (31/32 correct at 1 in flight, 7/32 at 2), so `dispatch_concurrency` above 1 is not usable and `max_wall_clock_s` cannot be re-derived until that defect is characterised.
The resolution is per-category, because the categories mean different things by "covered":
- **Needle retrieval may keep the 200K–1M range.** A needle does not require full coverage — finding it by REPL prescan and targeted windows is not sampling, it is the thesis (§2), and it is what the paper's models did unprompted. A needle task that exhausts the budget is a legitimate failure of the root's search strategy.
- **Aggregation/counting must be sized so full coverage FITS**, because that category exists to force coverage and punish sampling — grading a root for sampling on a corpus where exhaustive reading was never affordable would measure the budget, not the root. **CAP LOWERED v0.3.0: ~200K tokens (≈755K chars ⇒ ≤463 windows ⇒ ≤926 sub-calls)**, down from ~250K, which at 640/480 would need 1,042–1,158 sub-calls and no longer fits. And the wall clock binds well before the sub-call budget does: at the measured ~2.78 s per window serial, `max_wall_clock_s: 900` supports ~323 windows ≈ 139K tokens ≈ 525K chars before any root turn is charged. The "whichever binds first" rule therefore selects the wall clock today — which is exactly why `max_wall_clock_s` must be re-derived per size class (§9 S0) once concurrent dispatch is usable, and why no aggregation task may be authored against the 200K figure until it is. State each aggregation task's window count in the benchmark manifest so the affordability claim is checkable rather than assumed.
This is a pre-registration decision made while the benchmark does not yet exist; it is not tuning, and it must not be revisited after tasks are authored.

Categories:
- Needle retrieval in 200K–1M chars.
- Aggregation/counting across the full context (forces coverage, punishes sampling) — **corpus capped so full coverage fits the budgets, per the ceiling above**. **Rule:** at least one aggregation task must defeat deterministic string matching — requiring semantic judgment per item, verified at authoring by showing a pure-regex solution scores at chance — and at least one must be regex-solvable, so the benchmark rewards the root choosing code over leaf calls when code suffices. This keeps the S4 signal decomposable into root-as-programmer vs root-as-orchestrator-of-leaves, and stops strategy templates from quietly turning the category REPL-only while the leaf-reliability surface (R5, R12) ships unmeasured.
- Multi-document synthesis with checkable claims.
- Repo-level code QA.
- At least one adversarial-context task (R12: injection-shaped text in the corpus).

**Scoring & inference (pre-registered; changing any of this after runs exist is p-hacking):**
- **Primary artifact:** the per-task × per-arm × per-seed outcome grid, not two aggregate rates.
- **Decision rule (unchanged in kind):** a task passes for an arm if ≥2/3 seeds pass; success rate = tasks passed / N; "beats" = margin of **+2 tasks (N=20) or +3 tasks (N=30)** against each baseline. A tie with any baseline fails the S4 gate; a tie-or-loss to B2 additionally triggers the pivot-to-B2 rule; a tie-or-loss to B3 records a pivot-to-RAG finding of the same standing.
- **Inference layer (mandatory in the verdict, decision rule unchanged):** for each RLM-vs-baseline pair, the exact sign (McNemar) test over discordant tasks, and a 10,000-resample task-level paired bootstrap CI on the success-rate delta using fractional per-task scores (0, 1/3, 2/3, 1 over seeds). The S4 verdict states the p-value and CI next to the margin. (Context: under a no-difference null, +2/20 passes by luck roughly a third of the time — the verdict must carry its own evidential weight.)
- **Escalation (pre-registered at freeze):** if the net margin against any baseline lands in {+1, +2, +3} tasks, run seeds {4, 5} on the discordant tasks only for that pair and re-decide those tasks on ≥3/5 — removes threshold-flip noise exactly where the decision is made, at a bounded cost (typically 8–32 extra episodes). After escalation, escalated tasks score fractionally in fifths (0..5/5); the sign test and bootstrap are recomputed **once** on the final grid, and the verdict reports both pre- and post-escalation p/CI. No other recomputation is permitted.
- **Scheduling:** runs execute in (task, seed) blocks adjacent in time across all arms, so R9 thermal drift cancels within each paired comparison. "Interleaved" means this, not round-robin by arm. Within-block arm order is pre-registered: RLM then B2 on the resident topology, then one leaf relaunch serves B1 and B3 back-to-back — bounding server relaunches at two per block. **CORRECTION (v0.2.6): that relaunch must be `--parallel 2 -c 524288`, not `--parallel 1 -c 262144`, and B1 and B3 must each take their OWN slot.** As pre-registered, B1's document and B3's document land on slot 0 of one process — which is R13's smallest reproducing case verbatim (two documents, one slot), in the configuration measured at 4/18 leaked. The fix is free; leaning on R13's growth heuristic to protect the arms RLM is measured against would repeat the exact mistake R13 already cost us once.
- **Contamination is a BIAS CHANNEL that pointed at this benchmark's own null hypothesis (v0.2.6) — the most important thing R13 means for §8.** The arms do not split 3-vs-1 as first assumed: B3 is a **single-shot** arm (it shares only the C2 chunker, not the leaf's slot pool), so the split is **two chunked-and-exposed (RLM, B2) versus two single-shot-and-spared (B1, B3)**. Undetected slot contamination would therefore have degraded RLM and B2 while sparing BOTH controls — and under the decision rule above, a tie-or-loss to B2 triggers the pivot-to-B2 rule while a tie-or-loss to B3 records a pivot-to-RAG finding. **A serving-layer bug in a dependency would have manufactured both of the project's pre-registered kill findings simultaneously, and the write-up would have read as a clean, well-controlled negative result.** Nothing in this section's pre-registration would have caught it. Consequences, now binding: R13's foreign-string detector runs on every leaf call during S4 and its hit count is reported per arm in the verdict; and any future dependency shared unevenly across arms must be named in §8 as a candidate bias channel before the run, not after. Relaunch time is excluded from per-task wall-clock but included in the S0 cost projection; the quiesce + `/props` re-assertion covers correctness at each switch.
- `budget_kill` and `context_exhausted` episodes count as failures for **every** arm. `error` episodes are re-run once with the same seed (rows linked via `superseded_by`, §6); a second failure scores as a failure for that arm. Tokenized task length is recorded per episode.

**Cost scorecard (mandatory in the S4 report):** per-arm, per-task total tokens (tokens_in + tokens_out over all steps, retries included) and wall-clock, from the trace; energy in joules where available — the scaffold samples package power at 1 Hz (rocm-smi/hwmon, alongside the R9 temperature log) into `avg_power_w`/`energy_j`, enabled **only** if the S0 overhead check shows sampling does not perturb the numbers it measures (nullable otherwise; the named collectors are Linux-path — on a Windows host, `energy_j` stays null unless an equivalent is validated in the same S0 item). Interpretive rule: **any win claim states the cost multiple next to the margin** ("+3 tasks at N× median wall-clock and M× tokens vs B1/B2/B3") and includes a success-vs-cost Pareto chart. Deliberately no hard cost gate — the decision rule stays single.

**Per-category reporting:** the S4 report tables success per category per arm. **Zero-floor tripwire (pre-registered):** any category where RLM scores 0 while any baseline scores ≥3 of its tasks blocks a "clean pass" — the aggregate gate may still pass, but the verdict carries a mandatory named category-regression finding, and that category is the first post-S4 investigation. **Per-category margin gates are explicitly refused:** at 4–6 tasks per category any margin is noise, and a per-category gate would generate random vetoes of a valid aggregate result. This refusal is written down so the idea is not reinvented later.

**Chunk-size lock:** S4 runs RLM, B2, and B3 at the untouched config default (32K — Q1's admitted guess); the §7 #2 sweep is forbidden before the S4 verdict (sweeping RLM's main lever on benchmark-adjacent signal while B1 — the only chunk-independent arm — gets no analogous tuning would be test-set tuning); any post-S4 chunk-size change re-runs **all three chunked arms** (B2 and B3 share the C2 chunker verbatim, so the controls stay controlled) before any claim updates. The verdict line records `chunk_size`.

**Baselines (defined now, run in S4):**
- **B1:** leaf model, single shot, full 256K native context. Runs on a dedicated config profile (`--parallel 1 -c 262144`; ~2.8 GB KV at q8_0 on this arch), launched non-concurrently with the RLM topology. Overflow policy, pre-registered: tasks whose tokenized length exceeds the window are head+tail truncated to fit (50/50 split), and the truncation is recorded — the B1-infeasible subset must be identifiable in the results. (Does raw long context beat the scaffold?)
- **B2:** deterministic map-reduce — scaffold-only chunking (the C2 chunker, verbatim) → leaf summaries → root final. No RLM agency, no REPL.
- **B3:** deterministic BM25-RAG single shot — the C2 chunker verbatim; chunks indexed with DuckDB's FTS extension (BM25; DuckDB is already a dependency); chunks ranked against the task question; the B1 single-slot 256K profile filled to a pre-registered **80% of window**, restoring original document order; one call; same checkers. **No tunable k** — window-fill is the selection rule, fixed before freeze, so nothing is tuned on the benchmark. Pre-registered as a floor for deployable practice, not a ceiling on retrieval. (Is the scaffold worth more than the pipeline a practitioner would actually deploy?)

B2 is the honest control. If fixed map-reduce matches RLM on success rate, the root's agency is not earning its complexity and the project pivots to B2. B3 closes the blind spot B2 leaves open: without it, "beats B2 but loses to a free BM25 pipeline" would score as a project win.

## 11. Out of Scope

- **vLLM on this hardware.** Historically broken for months on gfx1151; upstream support merged ~Q1 2026 and community containers now work. Still out of scope: llama.cpp wins single-stream latency and operational simplicity for this topology, and one serving stack is enough.
- **NPU.** llama.cpp has no XDNA2 backend, and the NPU stacks that do exist (Lemonade, FastFlowLM) share the same 256 GB/s memory — the NPU cannot raise the decode ceiling. Excluded. **NPU auxiliary offload** (embeddings/rerankers) likewise: no auxiliary model exists in the minimal system, and a second inference stack is a new failure surface with no workload to serve.
- **Runtime world models / simulators** (I3). Lifecycle-only, S6-only.
- **Recursion depth > 1** until S4 evidence demands it.
- **Browser/pyodide sandboxing.** `subprocess` + rlimits (or Job Objects, A2) is sufficient for the threat model.
- **Multi-machine RPC clustering.** One box.
- **Any training** until S6 preconditions are met.
- **Decision records (v0.2 — evaluated and rejected; do not re-litigate without new facts):**
  - *KV/slot save-restore persistence across restarts.* The endpoint exists (`--slot-save-path`, POST /slots/{id}?action=save|restore) but hybrid recurrent-state serialization sits on the R8-fragile surface, and the avoided cost is ~seconds of prefix re-prefill per server lifetime.
  - *Eager dispatch of leaf calls parsed from an incomplete root turn.* Executes model output before the model finished emitting it (I1) and creates steps whose parent `repl_exec` does not exist yet (I4). The in-code alternative — the root using `asyncio.as_completed` to process early results — is already available in the REPL and belongs in strategy-template content.
  - *Root slot-2 speculative next-turn prefill.* The next turn extends slot 0's resident cache — only the ≤2,000-char observation prefills (<1 s); slot 2 also conflicts with single-slot MTP. (This incremental-cache fact is what §7 #3c protects.)
  - *Mid-episode RLM→B2 arm switching.* Makes the RLM arm's measured success rate asymptotically max(RLM, B2) — the margin rule and pivot trigger become unfalsifiable. Episode-level B2 fallback is admissible post-S4 in an operational mode only (fresh episode, `fallback_of` linkage — column added to §6 if/when the mode is built; benchmark runner asserts the mode off), never during benchmark runs.
  - *Content-adaptive variable chunk sizing.* Destroys per-call cost uniformity — the stated scheduling rationale for chunk sizing — and confounds the §7 #2 sweep. Boundary-snapping within ±10% (C2) captures the quality benefit at none of the scheduling cost.
  - *Scaffold-side relevance prefiltering (embeddings/BM25 deciding which chunks the root sees).* Usurps the coverage-vs-sampling decision the RLM thesis assigns to the root and the aggregation category exists to score; it would quietly convert the runtime into a RAG pipeline wearing an RLM costume. B3 (§8) is where retrieval competes — as a baseline, not inside the loop. The only admissible future form is a root-owned, read-only `rank_chunks()` utility, post-S4-gated on traces showing the root attempts ranking in the REPL and does it badly.
