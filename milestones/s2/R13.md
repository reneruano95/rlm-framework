# R13 — cross-request content leakage on a reused llama.cpp slot

Investigated 2026-08-13 with `milestones/s2/r13_repro.py`, which shares no code with
`milestones/s2/run_sweep.py` or `milestones/s2/leafcall.py`. Build `b10375-ba360efe1` (ROCm), reported
by the server's own `/props`.

**Headline: R13 is real and reproduces, but its stated mechanism is wrong.** The
leak is not caused by hybrid Gated-DeltaNet recurrent state. A full-attention
control model with no recurrent state at all leaks *more*. The leak is a
property of a llama.cpp **slot that has previously held a different document**,
and it survives every documented way of telling the server to forget.

---

## 1. The decisive experiment

One process, one model, one moment, byte-identical prompts. The only variable is
whether the answering slot has previously held a different document. Every
prompt in the replay was sent twice: once to pinned slot 0, which accumulates
chunks, and once to a slot that has only ever held that one chunk.

| arm | leaked | n | rate |
|---|---|---|---|
| shared pinned slot 0 | 24 | 54 | **44%** |
| one virgin slot per chunk (same process, same prompts) | 0 | 54 | **0%** |

Fisher exact, two-sided: **p = 4.4e-9**.

Because both arms run in the same process against the same weights with the same
sampler and the same prompt bytes, the difference cannot be the model, the
prompt, the corpus, the quantisation or the sampler. It is the slot.

`milestones/s2/results/r13_replay_paired.jsonl`.

## 2. Condition × leak-rate

A "leak" is an answer containing a string that (a) is absent from the document
that was actually sent, (b) is absent from the question, and (c) occurs in
exactly one *other* document in the corpus. Ordinary English words and echoes of
the question are therefore excluded by construction.

| # | condition | model | n | leaked | rate |
|---|---|---|---|---|---|
| 1 | shared pinned slot, `cache_prompt: true`, virgin server | hybrid 35B-A3B | 54 | 34 | 63% |
| 1b | shared pinned slot, paired run | hybrid 35B-A3B | 54 | 24 | 44% |
| 1c | shared pinned slot, server that had already served ~130 calls | hybrid 35B-A3B | 54 | 0 | 0% |
| 2 | **cold full re-prefill** (`timings.cache_n == 0`) | hybrid 35B-A3B | 6 | 2 | 33% |
| 2b | **cold full re-prefill** | gemma-4-12B | 6 | 4 | 67% |
| 3 | virgin slot per chunk, same process | hybrid 35B-A3B | 54 | 0 | 0% |
| 4 | fresh process per chunk | hybrid 35B-A3B | — | 0 | 0% (prior result, §RESULTS.md) |
| 5 | `POST /slots/0?action=erase` before every chunk | hybrid 35B-A3B | 54 | 33 | 61% |
| 6 | **architecture control, full attention** | gemma-4-12B-it | 54 | 39 | **72%** |
| 7 | synthetic two-prompt A→B, 7 conditions × 2 sizes × 5 trials | hybrid 35B-A3B | 70 | 0 | 0% |
| 8 | synthetic two-prompt size sweep, 522–8,551 tokens, cached and uncached | hybrid 35B-A3B | 40 | 0 | 0% |

Conditions 1–6 use the corpus in `milestones/s2/fixtures/`. Conditions 7–8 use documents
generated inside `r13_repro.py` with a UUID minted per trial.

The A→B→A order test, `id_slot` on a different slot, a changed `seed`, `n_keep:
0`, and `POST …?action=save` followed by `restore` were all run as part of
condition 7 and all sat at 0/5 — but see §5: condition 7 does not reproduce the
effect at all, so those are null results on a null instrument, not evidence that
those knobs work.

### The two rows that matter most

**Row 2 — it survives a cold full re-prefill.** The very first call against a new
chunk reports `timings.cache_n = 0`: nothing was reused from the prompt cache,
the whole prompt was prefilled from scratch. It still answers with the previous
chunk's content. Whatever carries the contamination is not the prompt cache.

**Row 5 — it survives explicit erase.** `POST /slots/0?action=erase` returns 200
and reports a truthful `n_erased` (1231, 2221, 4271, 8364, 16562 — matching the
resident prompt lengths). The slot's token cache really is being cleared, and
the leak rate is unchanged (61% vs 63%).

## 3. The architecture control — the hypothesis is falsified

**Control model: `gemma-4-12B-it-Q8_0`, architecture `gemma4`.** Confirmed two
independent ways rather than assumed:

* **GGUF metadata**: `gemma4.block_count = 48`; `gemma4.attention.head_count_kv`
  is a 48-entry array; `gemma4.attention.sliding_window = 1024` with a 48-entry
  `sliding_window_pattern`. **There is no `gemma4.ssm.*` key of any kind.**
* **Server loader at `-lv 4`**: `n_layer = 48`, `is_swa_any = 1`, `n_swa = 1024`,
  and llama.cpp allocates exactly two KV caches —
  `llama_kv_cache_iswa: creating non-SWA KV cache, size = 40960 cells` and
  `creating SWA KV cache, size = 1536 cells`. No recurrent state cache is
  created. (The `resolve_fused_ops: fused Gated Delta Net … enabled` lines in
  the log are backend kernel registration, not layers of this model.)

Every one of gemma-4's 48 layers is attention — full or sliding-window — and both
kinds are ordinary truncatable KV. It has no state that cannot be rewound.

For contrast, the leaf, verified the same way: `qwen35moe`, `block_count = 40`,
`full_attention_interval = 4` (so 10 attention layers and 30 recurrent),
`ssm.state_size = 128`, `ssm.conv_kernel = 4`, `ssm.inner_size = 4096`. Genuinely
hybrid, exactly as R13 assumed.

**The full-attention control leaked at 72% (39/54) against the hybrid's 63%, and
on 4 of 6 cold prefills against the hybrid's 2 of 6.** Per-chunk, the two models
track each other almost exactly:

| chunk | hybrid leaked | gemma leaked |
|---|---|---|
| s2-1024-p50 (1st) | 0/9 | 0/9 |
| s2-2048-p50 (2nd) | 3/9 | 3/9 |
| s2-4096-p50 (3rd) | 6/9 | 9/9 |
| s2-8192-p50 (4th) | 8/9 | 9/9 |
| s2-16384-p50 (5th) | 8/9 | 9/9 |
| s2-32768-p50 (6th) | 9/9 | 9/9 |

The R13/R8 hypothesis — "the per-slot recurrent state is not KV and is not
reset" — predicts that a model with no recurrent state cannot show this. It
shows it harder. **The hypothesis is falsified, and the finding is larger than
R13 stated: this is not a hybrid-architecture problem.**

## 4. Verbatim: leaked answer beside the true one

Identical prompt bytes, same process, same `cache_n`, same seed. Only the slot's
history differs.

**Chunk `s2-8192-p50`, literal question, trial 2.** The true answer is
`8243843a-ecc2-4f29-9122-60b53028b36b`.

> **shared slot 0** (`cache_n = 7798`)
> ```
> The provided text does not contain a custody note for the "Hurnshawfield
> Bureau." It contains custody notes for the "Prylfennwick Trust,"
> "Orstlornholm Trust," "Quinfennsted Trust," and "Selkdaleridge Bureau."
> Therefore, the requested key is not present in the excerpt.
> ```
> **virgin slot 4** (`cache_n = 7798`, same prompt)
> ```
> The archive key issued to the Hurnshawfield Bureau
> ```

Prylfennwick and Orstlornholm occur only in `s2-1024-p50`; Quinfennsted and
Selkdaleridge only in `s2-2048-p50`. The model is confidently enumerating the
contents of two documents it was shown earlier and has not been shown now.

**Chunk `s2-2048-p50`, absent-fact question, trial 1.** The question asks for a
key that is in no chunk.

> **shared slot 0**: `1251d802-86aa-4e75-96be-aefc175c1e8e` ← the **1024** chunk's key
> **virgin slot 2**: `0f3aac07-d1fe-460c-907f-53ddb57cc797` ← its own chunk's key, last digit wrong

## 5. Smallest reproducing case, and what would not reproduce

**Smallest reproducing case: two documents. A 1,021-token document, then a
2,045-token document, on the same slot.** The second document's answer returns
the first document's key. This is the earliest leak in all three independent
runs, identical to the call (`s2-2048-p50`, absent, trial 1) in the hybrid
virgin-server run, the hybrid paired run, and the gemma run. Leak rate then
climbs monotonically with the number of documents the slot has previously held:
0/9, 3/9, 6/9, 8/9, 8/9, 9/9.

**It would not reproduce on synthetic documents.** 110 trials of the clean
two-prompt design — one planted entity and a freshly minted UUID per document,
documents of 522 to 8,551 tokens, fact placed at 10%, 50% and 95% depth, across
`cache_prompt` true and false, same slot, different slot, A→B→A, changed seed,
`n_keep: 0`, and save/restore — produced **zero** leaks. Reproduction required
the `milestones/s2/fixtures/` corpus: long, low-entropy, near-duplicate procedurally
generated prose that the model itself repeatedly calls "nonsensical" and
"repetitive". Two probe designs also matter: an enumeration probe ("list every
custody key in this document") exposes the contamination far more readily than a
targeted question, because a targeted question lets a contaminated model hide
behind a terse refusal that happens to be correct.

This is a real limitation of the reproducer and it is why the upstream draft
ships the corpus rather than a generator.

## 6. Corrections to the R13 record

Three claims in `ARCHITECTURE.md` §10 R13 and `milestones/s2/RESULTS.md` §0 are not
supported by the data they cite.

1. **`/slots/{id}?action=erase` is not 501 on b10375.** It returns 501 only when
   the server was started without `--slot-save-path`, and so do `save` and
   `restore` — the message is explicit: `This server does not support slots
   action. Start it with --slot-save-path`. With `--slot-save-path <dir>` set,
   all three return 200 and `erase` reports a correct `n_erased`. The "cheap fix
   is unavailable" conclusion was a configuration artefact. It does not matter
   in the end, because erase does not fix the leak (§2 row 5) — but it was
   available to test all along.
2. **The final sweep (`milestones/s2/results/sweep.jsonl`, 117 calls) contains no leakage at
   all.** Auditing every answer against the chunk actually sent: 75 answers
   quoting an identifier quote one from their **own** chunk; 3 quote an
   identifier found in **no** chunk (`7a8b9c0d-1e2f-3a4b-5c6d-7e8f9a0b1c2d` is a
   fabricated placeholder); **zero** quote an identifier from another chunk. The
   sweep's headline quality numbers are therefore uncontaminated, which is
   consistent with it having been run one process per cell.
3. **The mechanism attribution is wrong** (§3). R8's hybrid/recurrent prompt-cache
   issues should *not* be recast as the cause of R13.

What the record got right, and this reproducer confirms: run 1
(`sweep-run1-shared-server.jsonl`) is genuinely contaminated; the prompts it sent
were correct (every `rendered_sha256` unique, every `chunk_sha256` matching the
fixture on disk, `rendered_chars` scaling with chunk size); the leaked strings
are unique to earlier chunks and are not near-misses of anything in the target
chunk (the closest UUID in the 4096 chunk to the leaked 1024 key has a similarity
ratio of 0.25); and a virgin slot or a virgin process is clean.

## 7. Mechanism — what the evidence supports, and what it does not

The evidence supports this and only this: **in llama.cpp b10375, a server slot
that has held one document can inject that document's content into the answer to
a later, unrelated document assigned to the same slot; this is independent of
model architecture, survives a full re-prefill in which `timings.cache_n` is 0,
survives an explicit `action=erase` that reports a truthful non-zero `n_erased`,
grows monotonically with the number of documents the slot has previously held,
and is eliminated completely by giving each document a slot that has held
nothing else.** Because the full-attention control leaks at least as much as the
hybrid, the contaminated state cannot be recurrent/SSM state; because a cold
prefill with zero cache reuse still leaks, it cannot be prompt-cache prefix
reuse; and because an erase that clears the right number of tokens does not stop
it, it is not the token-indexed cache that `n_erased` counts. That triangulates
to per-slot state outside the accounted KV cache — stale cells left addressable
beyond the truncation point, or slot metadata not reset on document change — but
this reproducer is black-box and **has not been confirmed against llama.cpp
source, and no specific code path is claimed.** The evidence does *not* support
any statement about which llama.cpp data structure is at fault, does not
establish whether the effect exists on non-ROCm backends or other builds, and
does not establish a leak rate for ordinary prose: every positive result here
comes from one low-entropy synthetic corpus, and 110 trials on cleaner synthetic
documents produced nothing.

## 8. Consequence for the project

Unchanged in force, changed in scope. The only measured-clean configurations
remain one process per chunk and one never-reused slot per chunk — but the
second is now measured directly (0/54, p = 4.4e-9) rather than inferred from 9
calls, and it is cheap: it costs a slot, not a process. `--parallel N` with a
scaffold-side "never reuse a slot for a second chunk" rule, restarting the server
every N chunks, is the mitigation the data actually supports. **The full-attention
fallback leaf listed in config as the R8 hedge does not help and should not be
priced as a mitigation for this.**
